Loco дозволяє написати одну реалізацію `BackgroundWorker` і одне місце виклику `perform_later`, а потім вибрати — через конфігурацію, а не зміну коду — чи чергуються задачі надійно в Redis, Postgres чи SQLite, чи взагалі не чергуються надійно. Ця сторінка пояснює дизайн, який робить таку заміну безпечною, а не покрокову інструкцію додавання воркера (це [Додати фонового воркера](/uk/docs/how-to/add-worker/) чи вичерпний перелік ключів конфігурації (це [Довідник конфігурації](/uk/docs/reference/configuration/#queue) і [Вибрати бекенд черги](/uk/docs/how-to/choose-queue-backend/).

## Один трейт, одне місце виклику, три бекенди

```rust
#[async_trait]
pub trait BackgroundWorker<A> {
    fn build(ctx: &AppContext) -> Self;
    async fn perform(&self, args: A) -> Result<()>;
    // + queue(), tags(), class_name(), perform_later(), perform_later_with_priority(),
    //   perform_all_later(), perform_all_later_with_priority()
}
```

Ви реалізуєте `perform`, реєструєте воркера в `connect_workers` і ставите задачу в чергу через `MyWorker::perform_later(&ctx, args).await?`. Нічого в цьому виклику не посилається на те, який бекенд активний — це вирішується повністю через `queue.kind` у конфігурації (`Redis` | `Postgres` | `Sqlite`), який читається під час boot у `create_queue_provider`. Це та сама перевага «конфігурація замість коду», про яку йдеться у [Чому «батарейки в комплекті»](/uk/docs/explanation/why-batteries-included/), застосована до надійності та семантики доставки: заміна бекендів — це операційне рішення (що вже працює у вашій інфраструктурі, який профіль затримки/пропускної здатності вам потрібен), а не переписування.

`perform_later` (і його побратим `perform_later_with_priority`) повертає `Result<String>` — ідентифікатор задачі — а не `Result<()>`. Це значення повернення важливе, бо саме його ви передали б у `cargo loco jobs cancel`/`requeue` або занотували для подальшого зіставлення; розглядайте будь-яке місце виклику `perform_later`, яке відкидає значення, як навмисний вибір не відстежувати задачу, а не як єдиний варіант.

Парна пакетна функція, `perform_all_later` і `perform_all_later_with_priority`, слідує тому самому контракту для багатьох задач одразу: один `Vec` ідентифікаторів назад, у порядку входу, і один обмін із чергою замість одного на задачу. Кожен вбудований провайдер реалізує `QueueProvider::enqueue_batch` атомарно — одна транзакція на Postgres/SQLite, конвеєр `MULTI`/`EXEC` на Redis — тож пакет або повністю ставиться в чергу, або не залишає нічого. Трейт має дефолтний `enqueue_batch`, який циклиться по `enqueue`, тож сторонній провайдер продовжує компілюватися й отримує пакетну семантику без атомарності, поки не перевизначить метод. Це віддзеркалює `ActiveJob.perform_all_later` у Rails, який повертається до окремих постановок у чергу на адаптерах без підтримки bulk.

## Два SQL-бекенди поділяють одну реалізацію

Черги Postgres і SQLite колись були двома незалежними паралельними реалізаціями, які доводилося синхронізувати вручну. З лінії 1.0 вони дедубліковані за одним внутрішнім трейтом `Driver`:

```rust no-syntax-check="trait sketch with `...` standing in for the real types"
pub(crate) trait Driver {
    type Pool;
    fn idle_count(&self) -> ...;
    async fn dequeue(pool: &Self::Pool, tags: &[String]) -> ...;
    async fn complete_job(pool: &Self::Pool, id: ..., interval: ...) -> ...;
    async fn fail_job(pool: &Self::Pool, id: ..., error: ...) -> ...;
}
```

Модель `Job`, цикл опитування/реєстрації (`JobRegistry`), перехоплення панік навколо `perform` і механізм робочого циклу живуть один раз, узагальнені над `Driver`. `PgDriver` і `SqliteDriver` мають постачати лише три операції БД вище плюс тип пулу — усе інше (реєстрація воркерів, фільтрація за тегами, граціозне скасування) — спільний код, а не дві копії, які можуть розійтися. Саме тому Postgres і SQLite мають ідентичну *поведінку* (ті самі адміністративні операції, та сама семантика пріоритету, той самий життєвий цикл задачі), хоча лежачий SQL обов'язково різний — один використовує `FOR UPDATE SKIP LOCKED` для конкурентного вилучення, інший імітує це таблицею блокувань, бо SQLite не має еквівалента. Redis, будучи архітектурно іншим (без SQL, без блокувань рядків), тримає власний незалежний робочий цикл замість реалізації `Driver` — але ззовні все одно підпорядковується тому самому зовнішньому контракту (той самий API `Queue`, той самий життєвий цикл задачі, ті самі адміністративні операції).

Саме цей спільний контракт дозволяє `cargo loco jobs cancel|tidy|purge|dump|import|requeue` працювати однаково, незалежно від того, який бекенд налаштований — включно з Redis, який історично відставав від SQL-бекендів у підтримці адміністративних операцій, але тепер досяг паритету.

## Пріоритет: одна семантика, три стратегії зберігання

Усі три бекенди вилучають задачі спочатку за пріоритетом, потім за віком: вище значення пріоритету `i32` — терміновіше, при рівності перевага ранішому `run_at`, потім стабільному ідентифікатору задачі. Те, як кожен бекенд *зберігає* цей порядок, відрізняється залежно від його моделі зберігання, і це варто розуміти, бо воно пояснює відносні сильні сторони бекендів:

- **Postgres / SQLite** додають стовпець `priority` і `ORDER BY priority DESC, run_at, id` під час вилучення (існуючі таблиці до 1.0 автоматично мігруються з додаванням стовпця). Це природне рішення для рядкового сховища з планувальником запитів.
- **Redis** не має планувальника запитів, на який можна спертися, тому пріоритет закодовано структурно: задачі живуть у відсортованій множині (ZSET), оціненій за *негативним* пріоритетом, тож найпріоритетніша задача сортується першою у зростаючому порядку `ZRANGE` — з `run_at`/id як явним розрізненням рівності в логіці вилучення, адже одна оцінка не може нести три рівні впорядкування.

Redis додатково підтримує **іменовані черги** (`queue.queues: [high, low, ...]`, перша = найважливіша) з двома незалежними воркерами, підкріпленими дефолтними чергами `["default", "mailer"]`, і перевизначення `Worker::queue()`, щоб спрямовувати задачі конкретного воркера в одну з них. Це грубіший інструмент, ніж пріоритет на задачу — іменовані черги розділяють, *який пул воркерів* забере задачу, тоді як `priority` вирішує порядок *всередині* цього пулу — і вони комбінуються (іменована черга все ще може бути впорядкована за пріоритетом всередині).

## Режими воркерів: обмін надійності на простоту

`workers.mode` — це окрема вісь від бекенду черги — вона вирішує, чи постійна черга взагалі бере участь у картині:

| Режим | Надійно при перезапусках? | Де виконуються задачі | Типове застосування |
|---|---|---|---|
| `BackgroundQueue` (за замовчуванням) | так | окремий процес/потік воркера, вилучає з налаштованого бекенду `queue:` | продакшн |
| `ForegroundBlocking` | не застосовно — виконується вбудовано | викликаючий запит/таск, синхронно | тести, де потрібне детерміноване виконання перед перевіркою побічних ефектів |
| `BackgroundAsync` | ні — втрачається при падінні | `tokio::spawn` у тому самому процесі | малозначна, найкраща-спроба робота, де розгортання бекенду черги не варте того |

Причина, чому це перемикач режимів, а не різниця в коді, та сама, через яку бекенд — перемикач конфігурації: `perform_later` і `perform` не змінюються, тож воркер, написаний і протестований під `ForegroundBlocking`, поводиться ідентично після переключення застосунку на `BackgroundQueue` у продакшні — змінюється лише *коли* і *де* `perform` справді виконується, а не його логіка.

## Вибір бекенду

Немає універсально правильного вибору — три бекенди торгуються за реальними інфраструктурними осями:

- **Redis** — найменша затримка, іменовані/пріоритетні черги, немає схеми для обслуговування; правильний дефолт, якщо Redis уже є частиною вашого стеку.
- **Postgres** — жодної нової інфраструктури, якщо основна база даних вашого застосунку вже Postgres, і `FOR UPDATE SKIP LOCKED` дає солідну пропускну здатність для конкурентних воркерів.
- **SQLite** — взагалі нуль додаткової інфраструктури, добре для малих розгортань чи локальної розробки; резервний варіант із таблицею блокувань для конкурентності робить його менш придатним для великої кількості конкурентних воркерів, ніж два інші.

Дивіться [Вибрати бекенд черги](/uk/docs/how-to/choose-queue-backend/) для конкретної конфігурації кожного, і [Довідник конфігурації](/uk/docs/reference/configuration/#queue) для кожного поля та його дефолту.
