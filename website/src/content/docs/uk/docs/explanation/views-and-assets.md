«Як ця відповідь потрапляє до браузера» має три різні форми в застосунку Loco — відрендерений на сервері HTML, JSON API за окремо збудованим SPA, або повністю вбудований одиночний бінарник — і Loco дозволяє вибрати, не змінюючи того, як працюють контролери. Ця сторінка пояснює модель за цим вибором. Як писати конкретне відображення чи підключити статичний мідлвар — дивіться [Рендер серверних відображень](/uk/docs/how-to/render-views/); вичерпні ключі мідлварів/конфігурації — [каталог мідлварів](/uk/docs/reference/middleware/) і [довідник feature-прапорців](/uk/docs/reference/feature-flags/).

## Розділення, про яке контролерам не треба дбати

Loco зберігає традиційний поділ обов'язків — контролер парсить запит і викликає моделі; *відображення* відповідає лише за формування фінальної відповіді — і робить цей поділ конкретним одним трейтом:

```rust
pub trait ViewRenderer {
    fn render<S: Serialize>(&self, key: &str, data: S) -> Result<String>;
}
```

Контролер ніколи не розмовляє з Tera, чи з будь-яким конкретним шаблонним двигуном, прямо — він приймає `v: impl ViewRenderer` (зазвичай через екстрактор `ViewEngine<E>`) і викликає `format::render().view(&v, "home/hello.html", data!({..}))`. Двигун за цим трейтом вирішується один раз, на рівні `Initializer` — замініть `ViewEngine<TeraView>` на `ViewEngine<YourEngine>`, і кожне існуюче місце виклику продовжить компілюватися, бо воно було пов'язане лише з трейтом, а не з Tera конкретно. Це той самий шаблон «аварійного виходу», описаний у [Чому «батарейки в комплекті»](/uk/docs/explanation/why-batteries-included/): Tera — вбудоване, `ViewRenderer` — шов, яким ви користуєтесь, якщо потрібне щось інше.

Для чистих JSON API «відображенням» може бути просто структура `#[derive(Serialize)]`, сформована руками і повернута через `format::json(..)` — жодного шаблонного двигуна в циклі взагалі. Більшість справжніх застосунків поєднують обидва: JSON-відображення для API-поверхні, Tera-відображення для кількох відрендерених на сервері сторінок (адмін-панель, маркетингова сторінка, лендінг підтвердження електронної пошти).

## Три форми розгортання, один набір коду контролерів

### Відрендерення на сервері (Tera)

Форма за замовчуванням: `TeraView` читає шаблони з `assets/views/**/*.html` на диску під час запиту, поряд зі статичними файлами, які обслуговуються з `assets/static/` через мідлвар `static`. Це природний вибір, коли сам застосунок рендерить HTML, який отримує браузер — шаблони можна редагувати без перескладання (`cargo loco start` підхоплює змінений `.html` файл на наступному запиті), що важливо під час активної розробки UI.

### Відрендерення на клієнті (SPA)

Тут робота Loco стискається до двох речей: обслуговувати JSON API і обслуговувати *збудовані* статичні ресурси SPA (вивід у стилі `dist/` окремої збірки фронтенду) через той самий мідлвар `static`, зазвичай із fallback до `index.html` для клієнтського роутингу. `TeraView` взагалі не бере участі в API-поверхні — розділення між «бекенд віддає дані» та «фронтенд володіє рендерингом» є повним, а роль Loco — просто: контролери API плюс статичний файловий сервер, націлений туди, куди приземляється збірка фронтенду.

### `embedded_assets`: один прапорець, дві підсистеми замінені разом

`embedded_assets` — це build-часова Cargo-функція, яка змінює, *звідки беруться байти*, не змінюючи жодного виклику контролера чи відображення:

```toml
loco-rs = { version = "...", features = ["embedded_assets"] }
```

Із нею увімкненою, вся тека `assets/` — шаблони *і* статичні файли — сканується під час компіляції і вбудовується прямо в бінарник. Те, що робить це варим окремого архітектурного поняття, а не просто «меншим розгортанням», — це те, що замінюється не одна підсистема: **обидві** — Tera-двигун відображень і мідлвар статичних ресурсів — одночасно замінюються варіантами, що читають із вбудованих даних (`views::engine_embedded` на місці `views::engine`, `static_assets_embedded` на місці `static_assets`) за тим самим гейтом `#[cfg(embedded_assets)]`. Один прапорець перевертає дві незалежно зареєстровані підсистеми синхронно, тож пошук шаблону і запит статичного файлу обидва розв'язуються проти тієї ж самої таблиці ресурсів у бінарнику, а не один читає диск, а інший — пам'ять. З коду застосунку нічого не змінюється — ключі конфігурації `ViewEngine`/`ViewRenderer` і статичного мідлвара ідентичні в обох випадках.

Компроміс — дзеркальне відображення зручності живого редагування SSR: розгортання одиночним бінарником з атомарними оновленнями коду/ресурсів і жодної теки ресурсів у файловій системі для обслуговування в продакшні, ціною повної перекопіляції при будь-якій зміні ресурсу і більшого бінарника. Проєкти часто використовують звичайні ресурси на файловій системі в розробці (швидка ітерація) і вмикають `embedded_assets` для release-збірок (простіше розгортання) — той самий код контролерів і відображень працює без змін в обох.

## Чому це один прапорець, а не перемикачі на підсистему

Було б можливо дозволити двигун відображень і статичний мідлвар вбудовуватися незалежно — але це створило б форми розгортання, де шаблони запечені в бінарник, тоді як статичні файли читаються з диска (чи навпаки), без чіткої операційної вигоди і з реальною загрозою, що дві розійдуться (перескладання оновлює вбудовані шаблони, але не окремо розгорнуту теку статичних файлів, чи навпаки). Пов'язування обох під одним feature-прапорцем робить «вбудоване» єдиним, злагодженим режимом розгортання, а не матрицею часткових станів, про які треба міркувати — у згоді з ширшою темою [Чому «батарейки в комплекті»](/uk/docs/explanation/why-batteries-included/) про стискання класу рішень в один добре протестований дефолт, з чітко позначеним способом відмовитися (тут — просто не вмикайте функцію).

Дивіться [Рендер серверних відображень](/uk/docs/how-to/render-views/) про конкретне розташування теки `assets/`, написання Tera-відображення та його проводку в контролері, і заміну на користувацький `ViewRenderer`; дивіться [довідник feature-прапорців](/uk/docs/reference/feature-flags/) про місце `embedded_assets` у повній матриці прапорців, і [каталог мідлварів](/uk/docs/reference/middleware/#8-static) про конфігураційні ключі мідлвара `static`.
