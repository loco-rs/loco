Rust не дозволяє звертатися до глобального змінного екземпляра застосунку так, як це можуть собі дозволити Rails чи Django — тут немає доступного всюди `current_app`, який можна змінювати з будь-якого місця. Відповідь Loco на питання «як обробник отримує доступ до бази даних, кешу, мейлера, мого власного клієнта сервісу?» — це єдина структура, яку дешево клонувати і яка проходить наскрізь через увесь застосунок: `AppContext`. Ця сторінка пояснює, чому ця структура має саме таку форму, і як `SharedStore` розширює її для речей, про які сам Loco не знає.

## `AppContext` як єдиний об'єкт спільного стану

Кожен обробник, фоновий воркер, таск і запланована задача в застосунку Loco отримують те саме значення `AppContext` — зібране один раз під час завантаження (див. [Архітектура](/uk/docs/explanation/architecture/) і дешево клоноване всюди, де воно потрібне, адже більшість його полів вже загорнуті в `Arc<...>` або інакше дешеві для клонування. Воно несе вісім полів:

```rust
#[derive(Clone, FromRef)]
#[non_exhaustive]
pub struct AppContext {
    pub environment: Environment,
    #[cfg(feature = "with-db")]
    pub db: DatabaseConnection,
    pub queue_provider: Option<Arc<bgworker::Queue>>,
    pub config: Config,
    pub mailer: Option<EmailSender>,
    pub storage: Arc<Storage>,
    pub cache: Arc<cache::Cache>,
    pub shared_store: Arc<SharedStore>,
}
```

Повний покроковий опис полів — типи, feature-гейти, призначення — живе в [AppContext & prelude](/uk/docs/reference/app-context/). Тут варте пояснення саме *проєктування*, а не перелік полів:

- **Одна структура, а не сім сервісів.** Замість того, щоб впроваджувати пул БД, кеш, мейлер, сховище та чергу як п'ять окремих частин стану Axum, Loco упаковує їх в одну `AppContext` і виводить для неї `FromRef`. Саме цей derive дозволяє обробнику попросити рівно той шматок, який йому потрібен — `State<DatabaseConnection>` чи `State<Arc<cache::Cache>>` — тоді як фоновий воркер або послідовність завантаження все ще можуть попросити все ціле. Ви отримуєте ергономіку вузького, однопризначеного вилучення без boilerplate-коду ручного написання impl `FromRef` для кожного поля.
- **`db` — єдине поле, яке не просто порожнє, а повністю випадає з компіляції.** Усі інші поля граціозно деградують, коли не налаштовані (`None` для `mailer`/`queue_provider`, драйвер `Null` для `cache`/`storage`) — застосунок без налаштованого мейлера все одно має поле `mailer: Option<EmailSender>`, просто встановлене в `None`. З `db` інакше: коли feature `with-db` вимкнена, поля взагалі не існує в структурі, що є способом сказати на рівні компіляції «ця форма розгортання справді не має бази даних», а не runtime `Option`, який викликаюча сторона може забути перевірити.
- **Це те саме значення всюди.** Оскільки `create_context` збирає `AppContext` рівно один раз під час завантаження, і кожна підсистема нижче — роутинг, мідлвари, обробники, `connect_workers`, таски, планувальник — отримує те саме значення, немає ризику, що обробник і фонова задача матимуть різні думки про те, який пул БД чи екземпляр кешу є «справжнім». Саме тому `Hooks::after_context(ctx: AppContext) -> Result<AppContext>` (який запускається одразу після зборки, перед побудовою роутів) — це єдиний хук, який може переписати сам контекст: це ваша остання й єдина можливість додати щось до нього, поки його не роздали всюди.
- **Воно позначене `#[non_exhaustive]`, тому збирається через білдер.** Позначення структури `#[non_exhaustive]` означає, що код застосунку не може ані написати літерал `AppContext { .. }`, ані скористатися синтаксисом функціонального оновлення — і саме тому додавання нового поля у наступному релізі Loco є незламною зміною. Замість цього `AppContext::builder(..)` приймає обов'язкові компоненти як аргументи та встановлює опціональні в no-op-провайдери за замовчуванням, а `ctx.into_builder()` перетворює існуючий контекст назад у білдер з усіма компонентами, які переносяться. Саме цей другий варіант слід використовувати в `after_context`: перезбірка з нуля мовчки викинула б мейлер, провайдер черги, кеш і спільне сховище, які boot уже встановив, тоді як зворотний обхід замінює один компонент і зберігає решту.

## Пролом, який фіксовані поля `AppContext` не можуть заповнити

Вісім полів `AppContext` покривають те, що потрібно *кожному* застосунку Loco. Вони, очевидно, не можуть покрити те, що потрібно *вашому* застосунку — клієнт стороннього API, хендл SDK feature-прапорців, специфічний для застосунку кеш попередньо обчислених даних. Існують дві опції, і вони не суперечать одна одній — це той самий дизайн, перенесений у два різні життєві цикли:

- **`Initializer`** (див. [Додати мідлвар](/uk/docs/how-to/add-middleware/) — це точка розширення *часу встановлення*: трейт із хуками `before_run`, `after_routes` і `check`, що використовується, щоб підключити цілий шматок інфраструктури до застосунку (зареєструвати Axum `Extension`, змонтувати шар сесій, встановити health-check для doctor).
- **`SharedStore`** — це точка розширення *зберігання*: місце, куди справді покласти значення типу, про який Loco ніколи не чув, щоб його можна було прочитати назад в обробнику, воркері чи будь-де, куди сягає `AppContext`.

На практиці вони комбінуються: ви зазвичай конструюєте значення, яким хочете поділитися, і викликаєте `ctx.shared_store.insert(..)` зсередини `Hooks::after_context` (той самий хук, що запускається один раз, одразу після зборки контексту), а потім читаєте його назад через екстрактор нижче.

## `SharedStore`: контейнер DI, ключований за типом

`AppContext.shared_store: Arc<SharedStore>` — це невелике, конкурентне, гетерогенне сховище — всередині `DashMap`, ключований за `TypeId`, тому воно може тримати по одному значенню будь-якої кількості різних типів `'static + Send + Sync` одночасно. Його API навмисно мінімальний:

| Метод | Що робить |
|---|---|
| `insert<T>(&self, val: T)` | Зберегти (або перезаписати) значення для типу `T`. |
| `get<T: Clone>(&self) -> Option<T>` | Отримати *клоновану* копію `T`, якщо вона є. |
| `get_ref<T>(&self) -> Option<RefGuard<'_, T>>` | Отримати запозичений охоронець `Deref<Target = T>` — для типів, які не `Clone`, або коли клонування було б марнотратним. |
| `remove<T>(&self) -> Option<T>` | Забрати значення назад. |
| `contains<T>(&self) -> bool` | Перевірити наявність, не торкаючись значення. |

### Читання назад: два шляхи і пастка найменування

Є два різні типи `SharedStore`, доступні з `loco_rs::prelude`, і сплутати їх — найпростіша помилка з цією функцією:

- **`loco_rs::app::SharedStore`** — тип-контейнер вище, який тримається як `ctx.shared_store`.
- **`loco_rs::controller::extractor::shared_store::SharedStore<T>(pub T)`** — *екстрактор* Axum `FromRequestParts<AppContext>`, також реекспортований як `SharedStore` з prelude, який сягає в `ctx.shared_store`, клонує `T` і віддає його вашому обробнику як звичайний аргумент:

```rust
#[debug_handler]
pub async fn index(
    SharedStore(service): SharedStore<MyClonableService>,
) -> impl IntoResponse {
    tracing::info!("api key: {}", service.api_key);
    format::empty()
}
```

Якщо `T` ніколи не було вставлено, екстрактор відхиляє запит із `Error::InternalServerError` — що є правильним режимом відмови для «застосунок забув щось підключити», на відміну від клієнтської 4xx. Для типу, який не `Clone`, пропустіть екстрактор і натомість скористайтеся `ctx.shared_store.get_ref::<T>()` безпосередньо через звичайне вилучення `State<AppContext>` — ви отримаєте лічильно-посилальний охоронець замість копії.

## Чому саме така форма, а не глобальний реєстр

Альтернативні дизайни знайомі з інших екосистем — синглтон service locator, або контейнер DI часу компіляції, який розв'язує граф залежностей. Loco навмисно уникає обох:

- **Глобальний змінний синглтон** — це те, що безпечний Rust не дає вам задарма, і вдаватися до `unsafe`/`OnceCell`-подібних глобалів, щоб його імітувати, означало б підривати ту саму гарантію (немає гонок даних, немає невидимих мутацій звідусіль), яка робить Rust вартим використання для сервера в першу чергу.
- **Фреймворк DI часу компіляції** (розв'язання графів конструкторів, згенерована макросами проводка) додає другу мову конфігурації поверх самого Rust для проблеми, яку `AppContext` разом із `SharedStore` уже вирішує ціною однієї пари `insert`/`get`.

`SharedStore` навмисно ближчий до «типізованого, потокобезпечного `HashMap<TypeId, Box<dyn Any>>`, який вам дають задарма», ніж до загального фреймворку DI — він не керує життєвими циклами, не розв'язує залежності між тим, що ви зберігаєте, і не нав'язує порядок реєстрації. Такий обмін: менше потужності, але немає нової ментальної моделі для вивчення, і він комбінується зі звичайною володінням Rust, а не обходить її. Для більшості застосунків «покласти клієнта в `after_context`, витягти його через `SharedStore<T>`» — це вся модель.

Дивіться [довідник AppContext & prelude](/uk/docs/reference/app-context/) для вичерпних сигнатур полів/методів, і [Додати мідлвар](/uk/docs/how-to/add-middleware/) для суміжного опрацьованого прикладу (користувацьке розширення у стилі `MiddlewareLayer`/`Initializer`, підключене до застосунку).
