Застосунок Loco має два різні часові проміжки, які варто тримати окремо в голові: **boot** (запускається один раз, збирає все, що потрібно застосунку) та **обробку запитів** (запускається на кожен HTTP-запит, через фіксований конвеєр). Ця сторінка проходить обидва і пояснює той самий елемент впорядкування, який дивує майже всіх уперше: мідлвари запускаються в *зворотному* порядку від того, як ви їх перелічуєте.

## Boot: від `StartMode` до запущеного застосунку

Все починається з `src/boot.rs`, керованого трейтом `Hooks`, який реалізує ваш `App` (вичерпний покроковий опис методів — у [Hooks trait](/uk/docs/reference/hooks/). На високому рівні:

```text
cargo loco start
   │
   ▼
Hooks::load_config(env)            → Config            (default: env.load())
   │
   ▼
create_context::<App>(env, config) → AppContext          (db, mailer, queue, cache, storage wired up)
   │                                  Hooks::after_context(ctx) can rewrite ctx here
   ▼
db::converge + bgworker::converge  (migrations / queue setup, if applicable)
   │
   ▼
run_app::<App>(mode, ctx)          → BootResult
   │   ├─ Hooks::before_run(&ctx)
   │   ├─ Hooks::initializers(&ctx) → before_run() on each Initializer
   │   ├─ Hooks::routes(&ctx)       → AppRoutes
   │   ├─ Hooks::before_routes / after_routes(router, &ctx)
   │   ├─ Hooks::middlewares(&ctx)  → Vec<Box<dyn MiddlewareLayer>>
   │   └─ after_routes() on each Initializer
   ▼
start::<App>(boot, server_config)  → binds the socket, spawns the scheduler if requested,
                                      calls Hooks::serve(...), prints the banner
```

Кожен метод `Hooks` у цьому ланцюзі має розумне значення за замовчуванням (дивіться точні сигнатури та дефолти в довіднику) — мінімальний `App` потребує лише реалізації `app_name`, `boot`, `routes`, `connect_workers`, `register_tasks` і (з базою даних) `truncate`/`seed`. Все інше — налаштування логування, завантаження конфігурації, стек мідлварів, проводка ініціалізаторів — це наданий метод, який ви перевизначаєте, лише коли треба його змінити.

### `StartMode`: що насправді запускається в цьому процесі

`boot()` отримує `StartMode`, який визначає, які підсистеми застосунку живі в *цьому* процесі:

| Режим | Сервер | Воркер | Планувальник |
|---|---|---|---|
| `ServerOnly` | так | ні | ні |
| `ServerAndWorker` | так | так (той самий процес) | ні |
| `ServerAndScheduler` | так | ні | так |
| `WorkerOnly { tags }` | ні | так, фільтровано за тегом | ні |
| `WorkerAndScheduler { tags }` | ні | так, фільтровано за тегом | так |
| `All` | так | так | так |

`StartMode` існує тому, що «вебсервер» і «те, що осушує чергу задач» не мусять бути тим самим процесом ОС — насправді для будь-чого поза розгортанням на одному dyno ви зазвичай *хочете* їх окремо, щоб масштабувати воркери та HTTP-рівень незалежно. `cargo loco start --worker`, `--server-and-worker`, `--scheduler` і `--all` відображаються прямо на ці варіанти (голий `cargo loco start` — це `ServerOnly`). Воркер насправді запускається лише якщо `workers.mode` у конфігурації — `BackgroundQueue`; дивіться [Модель фонової обробки](/uk/docs/explanation/background-processing-model/), чому.

### `AppContext` збирається один раз, тут

`create_context` — єдине місце, де вісім полів `AppContext` (`environment`, `db`, `queue_provider`, `config`, `mailer`, `storage`, `cache`, `shared_store`) отримують свої справжні значення, перед тим як `Hooks::after_context` отримає останній шанс допрацювати структуру (наприклад, покласти користувацький сервіс у `shared_store`). Усе нижче — роутинг, мідлвари, обробники, фонові воркери, таски, планувальник — отримує *те саме* значення `AppContext` (воно дешево `Clone`), саме тому це природне місце для спільного стану. Дивіться [AppContext та впровадження залежностей](/uk/docs/explanation/appcontext-and-di/) для повної історії цієї структури та її слота розширення `shared_store`.

## Обробка запиту: цибулина

Після завершення boot `AppRoutes::to_router` скомпілював ваші роути плюс стек мідлварів у один справжній `axum::Router<AppContext>`. Подорож запиту через неї виглядає так:

```text
   inbound request
        │
        ▼
┌───────────────────────────────────────────┐
│ powered_by            (outermost — first) │
│  ┌────────────────────────────────────┐   │
│  │ fallback (non-prod)                │   │
│  │  ┌──────────────────────────────┐  │   │
│  │  │ request_id                   │  │   │
│  │  │  ┌────────────────────────┐  │  │   │
│  │  │  │ logger                 │  │  │   │
│  │  │  │  ┌──────────────────┐  │  │  │   │
│  │  │  │  │ … cors, etag,    │  │  │  │   │
│  │  │  │  │   compression …  │  │  │  │   │
│  │  │  │  │  ┌────────────┐  │  │  │  │   │
│  │  │  │  │  │limit_payload│  │  │  │  │   │
│  │  │  │  │  │ (innermost)│  │  │  │  │   │
│  │  │  │  │  │  ┌──────┐  │  │  │  │   │
│  │  │  │  │  │  │handler│  │  │  │  │   │
│  │  │  │  │  │  └──────┘  │  │  │  │   │
│  │  │  │  │  └────────────┘  │  │  │   │
│  │  │  │  └──────────────────┘  │  │   │
│  │  │  └────────────────────────┘  │  │   │
│  │  └──────────────────────────────┘  │   │
│  └────────────────────────────────────┘   │
└───────────────────────────────────────────┘
        │
        ▼
    response, unwinding back out the same layers
```

### Чому порядок — LIFO

`AppRoutes::to_router` будує цю цибулину, викликаючи `app.layer(...)` по одному разу на мідлвар, у тому порядку, в якому їх перелічує `default_middleware_stack` (`limit_payload` перший, `powered_by` останній). `Router::layer` в Axum загортає *існуючий* роутер у кожен новий шар як новий **найзовніший** шар. Наслідок, сформульований прямо у власному коментарі вихідного коду фреймворку:

> "the LAST middleware is the FIRST to meet the outside world (a user request starting), or 'LIFO' order" — `src/controller/app_routes.rs`

Тож порядок у коді/конфігу й порядок під час виконання — протилежні: роути додаються першими (вони стають найвнутрішнішим ядром цибулини — тим, що зрештою загортає кожен шар), а *останній* доданий мідлвар (`powered_by`, внизу дефолтного списку) — це *перше*, через що входовий запит насправді проходить. `request_id` навмисно ближче до кінця списку (тобто ближче до *зовнішнього боку* під час виконання) саме тому, що кожен запит потребує призначення свого ID якнайраніше у своєму житті.

Це має практичне значення щоразу, коли ви звертаєтеся до `Routes::layer(...)`, щоб прикріпити `tower::Layer` до одного контролера, або перевизначаєте `Hooks::middlewares`, щоб переставити дефолтний стек, — переплутаєте напрямок, і мідлвар, який мав би запускатися перед автентифікацією, опиниться після неї. Повний упорядкований список із конфігураційним ключем кожного мідлвара та станом за замовчуванням — у [каталозі мідлварів](/uk/docs/reference/middleware/); [Додати мідлвар § 5](/uk/docs/how-to/add-middleware/#5-напишіть-власне-middleware) показує, як власноруч написати мідлвар `tower::Layer`, який бере участь у тій самій цибулині.

## Де це залишає обробник

До моменту, коли ваш обробник запускається, це просто звичайна функція-обробник Axum зі звичайними екстракторами Axum (`State<AppContext>`, `Json<T>`, `Path<T>` тощо — нічого специфічного для Loco не потрібно). Відповідна сторона цибулини симетрична: ваш `impl IntoResponse` (або допоміжні засоби `format::` в Loco) створює `Response`, який потім розкручується назад крізь той самий стек мідлварів у зворотному напрямку, і кожен шар отримує шанс допрацювати його (стиснення, заголовки, логування результату), перш ніж той покине процес.

Про механіку того, як роути отримують свою форму axum `Router<AppContext>` (`AppRoutes`, `Routes`, префікси, вкладення), дивіться [Додати контролер](/uk/docs/how-to/add-controller/); про те, як ця модель відображається на поняття чистого Axum, які ви вже знаєте, дивіться [Перехід з Axum](/uk/docs/explanation/coming-from-axum/).
