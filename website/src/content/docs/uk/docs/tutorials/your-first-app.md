Це найшвидший шлях від «нічого не встановлено» до «робочого API, яке ви створили самі». Ви встановите інструменти, згенеруєте новий застосунок Loco, запустите його, звернетеся до нього через `curl`, а потім додасте ресурс із підтримкою бази даних однією командою генератора. Кожен крок нижче має працювати рівно так, як описано — якщо щось не збігається з тим, що ви бачите, про це варто повідомити.

Вам потрібен робочий Rust-тулчейн (stable, через [rustup](https://rustup.rs)) і близько 10 хвилин. Попереднє знання Loco не припускається.

## 1. Встановіть інструменти

Loco постачається у вигляді двох речей: генератор застосунків `loco` (невеликий окремий CLI) та `loco-rs` — фреймворк, від якого залежить ваш згенерований застосунок. Також вам знадобиться `sea-orm-cli`, оскільки ваш застосунок використовуватиме базу даних.

```sh
cargo install loco
cargo install sea-orm-cli
```

## 2. Згенеруйте новий застосунок

Запустіть `loco new` з назвою застосунку та явно зазначеними прапорцями для бази даних, фонових воркерів і асетів. Коли всі чотири параметри вказані, запитувати нічого не залишається, тому майстер пропускає всі підказки — повністю детермінований, придатний для скриптів спосіб створення застосунку:

```sh
loco new --name hello_loco --db sqlite --bg async --assets none
```

```sh
🚂 Loco app generated successfully in:
hello_loco/
```

<div class="infobox">
Якщо каталог, у якому ви це запускаєте, сам знаходиться всередині git-репозиторію, <code>loco new</code> попросить підтвердження перед продовженням. Відповідайте <code>y</code> або передайте <code>-a</code>/<code>--allow-in-git-repo</code>, щоб повністю пропустити підказку.
</div>

Тепер у вас є папка `hello_loco/` із працездатним застосунком усередині. Ось та частина структури, яку ви торкатиметеся в цьому уроці:

| Шлях | Що там є |
|---|---|
| `src/app.rs` | З'єднує маршрути, воркери та завдання разом — єдиний файл, який прив'язує все до `Hooks`. |
| `src/controllers/` | Обробники запитів, один файл на ресурс. |
| `src/models/` | Ваші сутності бази даних (`_entities/`, згенеровані) та ваша власна логіка моделей. |
| `migration/src/` | Один файл на кожну зміну схеми, застосовуються послідовно. |
| `config/development.yaml` | Налаштування для середовища `development` — порт, URI бази даних, логування тощо. |

`--db sqlite` обрав SQLite (локальний файл, нуль налаштувань) як базу даних, `--bg async` запускає фонові завдання у тому самому процесі, а `--assets none` пропускає генерацію скафолда для серверних чи клієнтських представлень — ви будуєте чистий JSON API.

## 3. Запустіть сервер

```sh
cd hello_loco
cargo loco start
```

Ви побачите банер запуску Loco, а внизу — `listening on port 5150`. `cargo loco` — це не справжня підкоманда cargo, це Cargo-аліас (`loco = "run --"`), вбудований у `.cargo/config.toml` кожного згенерованого застосунку, тому `cargo loco start` насправді запускає власний бінарник вашого застосунку з `start` як аргументом.

Залиште його працюючим, а в іншому терміналі зверніться до вбудованої перевірки живлення — коду ще не написано, а він уже відповідає:

```sh
$ curl localhost:5150/_ping
{"ok":true}
```

`/_ping` — один із трьох вбудованих ендпоінтів моніторингу (`/_ping`, `/_health`, `/_readiness`), які монтує безумовно `AppRoutes::with_default_routes()` у `src/app.rs`.

<div class="infobox">
Оскільки ви обрали базу даних (<code>--db sqlite</code>), цей застосунок було згенеровано також із повним, готовим до використання набором автентифікації, змонтованим на <code>/api/auth/*</code> (реєстрація, вхід, поточний користувач тощо) — будь-який застосунок Loco з базою даних отримує його, це не специфічне для певного стартового «шаблону». Цей урок його не використовує; якщо хочете його дослідити, дивіться <a href="/uk/docs/tutorials/saas-with-auth/">Створіть невеликий застосунок з автентифікацією</a>.
</div>

Зупиніть сервер за допомогою `Ctrl+C`, перш ніж продовжити — ви перезапустите його після генерації коду.

## 4. Згенеруйте CRUD-ресурс

Ось тут Loco розкриває свою силу. **Скафолд** генерує міграцію бази даних, модель/сутність Sea-ORM, типізовані DTO для запитів/відповідей та повний CRUD-контролер — однією командою:

```sh
cargo loco generate scaffold posts title:string content:text --no-auth
```

Скафолд є **адаптивним** — не потрібно вибирати прапорець виду. У headless-застосунку (як цей) він створює контролер JSON API; якщо ваш застосунок має фронтенд React (`frontend/`), він також генерує типізовані хуки та сторінки для ресурсу. Вивід закінчується кількома підтверджувальними рядками:

```sh
* Migration for `posts` added! You can now apply it with `$ cargo loco db migrate && cargo loco db entities`.
* A test for model `Posts` was added. Run with `cargo test`.
* Controller `Post` was added successfully.
* DTO `PostDto` was added successfully.
```

<div class="infobox">
<strong>Чому <code>--no-auth</code>?</strong> Згенеровані скафолдом маршрути за замовчуванням захищені автентифікацією: кожен обробник приймає екстрактор <code>auth::JWT</code>, тому анонімний <code>curl</code> отримує <code>401 Unauthorized</code>. Це правильне значення за замовчуванням для справжнього ресурсу, але воно перетворило б цей урок на навчання автентифікації. <code>--no-auth</code> генерує той самий контролер з публічними маршрутами. Щоб побачити варіант із автентифікацією — реєстрацію, вхід, надсилання bearer-токена — пройдіть <a href="/uk/docs/tutorials/saas-with-auth/">Створіть невеликий застосунок з автентифікацією</a>.
</div>

На відміну від простого генератора `migration`, `scaffold` (як і `model`) вже **застосував** міграцію та перегенерував сутності Sea-ORM за вас — вручну запускати більше нічого не потрібно. Тепер у вас має бути:

```
src/
  controllers/posts.rs      <- CRUD handlers + routes
  dtos/posts.rs             <- request/response types
  models/_entities/posts.rs <- generated Sea-ORM entity
  models/posts.rs           <- your extension point
migration/
  src/mYYYYMMDD_HHMMSS_posts.rs
```

`title:string` і `content:text` тут обидва є nullable-колонками (без суфікса `!`/`^`) — це навмисно, щоб перший прохід залишався простим. Суфікси типів полів (обов'язкове, унікальне) та повний список типів розглядаються в [Генератори та типи полів](/uk/docs/reference/generators/).

## 5. Запустіть і викличте свій новий ендпоінт

```sh
cargo loco start
```

В іншому терміналі створіть пост:

```sh
$ curl -X POST -H "Content-Type: application/json" -d '{
  "title": "My first Loco post",
  "content": "It works."
}' localhost:5150/api/posts

{"id":1,"title":"My first Loco post","content":"It works.","created_at":"...","updated_at":"..."}
```

І отримайте список назад:

```sh
$ curl localhost:5150/api/posts
{"items":[{"id":1,"title":"My first Loco post","content":"It works.","created_at":"...","updated_at":"..."}],"page":1,"page_size":25,"total_pages":1,"total_items":1}
```

Ендпоінт списку є посторінковим, тому він відповідає конвертом сторінки, а не простим масивом. `page` і `page_size` — це параметри запиту — `curl 'localhost:5150/api/posts?page=2&page_size=10'` — а назви полів метаданих ті самі, що використовують власні [допоміжні засоби пагінації](/uk/docs/how-to/paginate/) фреймворку.

Це повний цикл: згенерована міграція створила таблицю `posts`, згенерована сутність Sea-ORM змоделювала її, а згенерований контролер виставив її через HTTP — без жодного рядка Rust, написаного вручну.

## Що ви побудували

За кілька хвилин, не написавши жодного рядка Rust самостійно, ви:

- Встановили Loco CLI та `sea-orm-cli`.
- Згенерували новий застосунок явною, відтворюваною командою `loco new`.
- Запустили його та викликали два вбудовані ендпоінти (`/api`, `/_ping`).
- Згенерували повний CRUD API для ресурсу `posts` та випробували його через `curl`.
