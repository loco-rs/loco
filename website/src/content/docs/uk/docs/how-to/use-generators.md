Мета: створювати скафолди коду застосунку (моделі, міграції, контролери, воркери, мейлери, файли розгортання, ...) зі вбудованих шаблонів Loco замість того, щоб писати шаблонний код вручну.

## 1. Знайте обмеження: лише debug-збірки

`cargo loco generate` (аліас `g`) компілюється лише в debug-збірках — `#[cfg(debug_assertions)]` охоплює весь цей підкомандний блок (`src/cli.rs`). Він доступний щоразу, коли ви запускаєте застосунок звичайним способом розробки (`cargo run`, `cargo loco start`, `cargo test`), але його **немає в `--release`-бінарнику**. `model`/`migration`/`scaffold` додатково залежать від фічі `with-db` (увімкнена за замовчуванням).

## 2. Запустіть генератор

```sh
# порожня модель (сутність + міграція + тест)
cargo loco generate model posts

# модель з типізованими полями
cargo loco generate model posts title:string! content:text

# повний CRUD-ресурс: сутність + міграція + контролер + маршрути + тести
cargo loco generate scaffold posts title:string! user:references

# лише контролер, без моделі/міграції (дія `index` генерується завжди,
# тому вказуйте лише додаткові дії, які вам потрібні)
cargo loco generate controller posts show publish

# генератори, що не стосуються БД
cargo loco generate task cleanup_old_sessions
cargo loco generate worker send_digest
cargo loco generate mailer welcome
cargo loco generate scheduler
cargo loco generate data countries
cargo loco generate deployment docker
```

Кожен генератор пише файли відносно кореня проєкту та виводить список того, що створив (а для `model`/`migration`/`scaffold` ще й додає рядок `mod` у відповідний `mod.rs`).

## 3. Виберіть потрібний вид

| Вид | Потрібна `with-db` | Що ви отримуєте |
|---|---|---|
| `model` | так | Сутність Sea-ORM + файл моделі + міграція + стартовий тест у `tests/models/` |
| `migration` | так | Окремий файл міграції (додавання/видалення колонок, з'єднувальні таблиці або порожній стаб — виводиться з назви) |
| `scaffold` | так | Повний CRUD: сутність, міграція, DTO, контролер, маршрути, тест моделі — плюс типізовані React-хуки/сторінки, якщо в застосунку є `frontend/` |
| `controller` | ні | Контролер + маршрути + тести, без моделі |
| `task` | ні | Стаб разової/CLI-задачі, який реєструється автоматично |
| `scheduler` | ні | Стартовий файл `config/scheduler.yaml` |
| `worker` | ні | Стаб фонового воркера, який реєструється автоматично |
| `mailer` | ні | Структура мейлера + вбудовані шаблони `subject`/`html`/`text` |
| `data` | ні | Структура завантажувача даних + статичний `data/<name>/data.json` |
| `deployment` | ні | Файли розгортання `docker`, `nginx` або `lambda` |
| `override` | ні | Копіює вбудований шаблон локально, щоб ви могли його редагувати — див. [Перевизначення вбудованих шаблонів](/uk/docs/how-to/override-templates/) |

`scaffold` і `controller` є **адаптивними** — без прапорця виду. За замовчуванням вони генерують JSON API, а скафолд додатково створює типізовані React-хуки/сторінки, якщо в застосунку є `frontend/`. (Старі прапорці `--api`/`--html`/`--htmx` було видалено в 1.0: `--api` досі приймається як no-op, щоб існуючі команди продовжували працювати; server-rendered HTML/HTMX-подання було замінено React SPA-фронтендом.)

Згенеровані маршрути за замовчуванням вимагають JWT, тому запит `curl` без bearer-токена повертає `401` — передайте `--no-auth`, щоб зробити ресурс публічним. Згенерований `controller` за замовчуванням публічний; `--auth` — його дзеркальна опція. Див. [Автентифікація на згенерованих маршрутах](/uk/docs/reference/generators/#автентифікація-на-згенерованих-маршрутах).

Це лише стислий огляд для орієнтації — вичерпний, перевірений словник усіх видів, усіх прапорців і правил виведення назв міграцій знаходиться в [довіднику генераторів і типів полів](/uk/docs/reference/generators/); сирі форми CLI-прапорців також є в [довіднику CLI](/uk/docs/reference/cli/#24-підкоманди-generate).

## 4. Використовуйте міні-мову типів полів

`model`, `migration` і `scaffold` приймають пари `name:type` після назви ресурсу. Повна таблиця ~50 базових типів (з варіантами суфіксів `!`/`^`, арностями та типами Rust) знаходиться в [довіднику міні-мови типів полів](/uk/docs/reference/generators/#мінімова-типів-полів) — перевірте її, перш ніж вгадувати назву типу. Кілька важливих фактів, які варто пам'ятати під час набору списку полів:

- Без суфікса = nullable (`Option<T>`); `!` = обов'язкове; `^` = унікальне (передбачає обов'язковість). Не кожен тип має форму `^` (`bool`, `tstz`, `json` — не мають).
- **`int` — це `i64`/`BIGINT`** у Loco 1.0 (раніше був `i32`) — `big_int` є просто аліасом. Використовуйте `small_int`/`small_unsigned`, якщо потрібна 16-бітна колонка.
- `name:references` додає обов'язковий зовнішній ключ belongs-to (`name_id`); `name:references?` робить його nullable; `name:references:custom_id` (опційно з `?`) явно задає назву FK-колонки.
- Типи `array` приймають тип елемента другим сегментом через двокрапку: `tags:array:string`, `scores:array!:int`.

```sh
cargo loco generate model movies long_title:string director:references award:references:prize_id
```

## 5. Застосуйте згенеровані міграції

Генерація `migration` (окремо або через `scaffold`/`model`) лише пише файл — вона не торкається бази даних. Застосуйте її та перегенеруйте сутності:

```sh
cargo loco db migrate && cargo loco db entities
```

## Перевірте це

```sh
cargo build          # генераторам потрібна debug-збірка, щоб взагалі бути доступними
cargo loco generate model posts title:string!
cargo loco db migrate
cargo test
```

Успішний запуск генератора виводить список створених/змінених файлів; `cargo build` (або `cargo check`) потім підтверджує, що згенерований код компілюється, а `cargo test` запускає стартовий тест, який генератор створив для вас.
