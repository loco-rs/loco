**Мета:** ізолювати рядки, що належать орендарям, в одній спільній базі даних, утримуючи активного орендаря явним у коді застосунку.

Loco надає три опційні трейти: `TenantEntity` ідентифікує колонку орендаря сутності, `TenantQueryExt::in_tenant` фільтрує запити, а `TenantActiveModelExt::set_tenant` призначає орендаря активній моделі. Ідентифікатор орендаря передається явно, тож ці хелпери не залежать від стану на рівні запиту чи потоку.

## 1. Увімкніть можливість

Додайте `multi-tenancy` до можливостей наявної залежності `loco-rs`:

```toml
loco-rs = { version = "1", features = ["multi-tenancy"] }
```

Ця можливість типово вимкнена та вмикає `with-db`. Вона робить трейти доступними як з `loco_rs::model`, так і з `loco_rs::prelude`.

## 2. Позначте сутності, що належать орендарям

Згенеруйте таблицю орендарів та ресурс із зовнішнім ключем орендаря:

```sh
$ cargo loco generate model tenants name:string!
$ cargo loco generate model documents title:string! tenant:references
```

Реалізуйте `TenantEntity` у кожному власноруч написаному модулі моделі. Не редагуйте згенерований файл `_entities`:

```rust
use loco_rs::prelude::*;

pub use super::_entities::documents::{self, ActiveModel, Entity, Model};

impl TenantEntity for documents::Entity {
    type TenantId = i64;

    fn tenant_column() -> documents::Column {
        documents::Column::TenantId
    }
}
```

`TenantId` має відповідати типу, що зберігається в колонці орендаря, наприклад `i64`, `Uuid` чи `String`. Реалізуйте трейт лише на сутностях, що належать орендарям. Використовуйте міграції, щоб додати індекси та складені унікальні обмеження для значень, специфічних для орендаря, наприклад `(tenant_id, title)`, коли назви документів мають бути унікальними в межах одного орендаря.

## 3. Розв'яжіть довіреного орендаря

Розв'язуйте орендаря з автентифікованих даних, а потім перевіряйте членство перед виконанням запиту з обмеженням за орендарем. Не довіряйте ідентифікатору орендаря з шляху, заголовка чи тіла запиту самому по собі.

Розв'язання орендаря та права доступу залишаються політикою застосунку. Розв'язувач може використовувати slug в URL, субдомен, claim у JWT або зв'язок через API-ключ, але зобов'язаний авторизувати того, хто викликає, для цього орендаря. У наведених нижче прикладах `tenant_id` — це результат цієї перевірки. Воркери можуть передавати ідентифікатор орендаря у своїх серіалізованих аргументах і перевіряти доступ під час виконання задачі.

## 4. Обмежте читання

`in_tenant` компонуеться зі звичайними фільтрами Sea-ORM:

```rust
let documents = documents::Entity::find()
    .in_tenant(tenant_id)
    .all(&ctx.db)
    .await?;

let document = documents::Entity::find()
    .filter(documents::Column::Id.eq(document_id))
    .in_tenant(tenant_id)
    .one(&ctx.db)
    .await?
    .ok_or(ModelError::EntityNotFound)?;
```

Згенерований SQL містить `documents.tenant_id = ?`; тож коректний ідентифікатор з-під іншого орендаря поводиться так, ніби рядка не існує.

## 5. Призначте орендаря під час створення

Використовуйте `set_tenant` після побудови нової активної моделі та перед вставкою:

```rust
let document = documents::ActiveModel {
    title: Set(params.title),
    ..Default::default()
}
.set_tenant(tenant_id)?
.insert(&ctx.db)
.await?;
```

Хелпер встановлює порожній ключ орендаря, приймає ідентичний ключ і повертає `ModelError::TenantMismatch`, якщо модель була попередньо заповнена іншим орендарем. Це не дає даним запиту перекрити довіреного орендаря. Невідповідність орендарю відображається на HTTP 400 зі стабільним кодом помилки `tenant_mismatch`.

## 6. Обмежте оновлення та видалення

Використовуйте обмежені групові білдери при зміні чи видаленні наявного рядка, що належить орендарю. Звичайне `.update()` активної моделі обмежує лише за первинним ключем.

```rust
let changes = documents::ActiveModel {
    title: Set(params.title),
    ..Default::default()
};

let updated = documents::Entity::update_many()
    .set(changes)
    .filter(documents::Column::Id.eq(document_id))
    .in_tenant(tenant_id)
    .exec(&ctx.db)
    .await?;

let deleted = documents::Entity::delete_many()
    .filter(documents::Column::Id.eq(document_id))
    .in_tenant(tenant_id)
    .exec(&ctx.db)
    .await?;
```

Перевіряйте `rows_affected`, коли ваш ендпоінт має розрізняти успіх від відсутнього чи міжорендарного ідентифікатора.

## Обсяг та обмеження

Ці трейти не обмежують автоматично кожну операцію з базою даних. Виклик Sea-ORM без `.in_tenant(...)` залишається необмеженим, що зручно для авторизованого адміністрування між орендарями, звітності та міграцій. Аудитуйте запити до даних орендарів на наявність цього фільтра.

`in_tenant` фільтрує цільову сутність; він не обмежує приєднані таблиці та не перевіряє рядки, на які посилаються. Перевіряйте, що пов'язані записи належать тому самому орендарю, та забезпечуйте це на рівні бази даних, де можливо. Будуйте поля мутацій явно, щоб клієнти не могли змінити належність орендарю через групові оновлення. Хелпери не встановлюють безпеку на рівні рядків у базі даних і не надають керування членством, ролями чи підписками.
