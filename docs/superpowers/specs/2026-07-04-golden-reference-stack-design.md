# Golden Reference Stack — Design Spec (Workstream 1)

Part of the 2026-07-04 "dark areas" program
(`docs/superpowers/audits/2026-07-04-dark-areas/DARK-AREAS-AUDIT.md`). This is the FIRST workstream:
hand-build one real Loco app on the decided flagship stack, prove it compiles + runs end-to-end, and
freeze it as the **exact target the rebuilt generator will reproduce**. No generator work here — this
de-risks the frontend bet and defines the contract everything downstream generates toward.

**Goal:** A working reference app: Loco JSON API + `ts-rs`-derived TypeScript bindings + a Vite/
React/react-router/TanStack Query SPA consuming a generated typed client, with JWT auth, served in
dev (Vite proxy) and prod (Loco serves the built SPA).

**Non-goals (explicitly deferred):** the generator rebuild (workstream 2), feature consolidation
(3), the correctness harness (4), OpenAPI/utoipa (deferred to the `--api` headless story), SSR, and
real-time. Keep this to the CRUD + auth happy path across one resource (`Post`) rich enough to
exercise the hard type cases.

---

## Decisions inherited (from the audit + spikes)

- **Typed contract = `ts-rs` derive, NOT OpenAPI.** Rust DTOs `#[derive(TS)]` → `.ts` bindings →
  typed fetch client + TanStack Query hooks. Spike-validated: cleanest TS for enums/generics,
  structurally can't drift.
- **Client stack:** Vite + React + react-router (v8 data router) + TanStack Query (v5).
- **Serving:** dev = Vite dev server proxying `/api` → Loco `:5150`; prod = Loco serves
  `frontend/dist` static with SPA `index.html` fallback (already supported by the `static_assets`
  middleware with `uri: "/"`; the `client` asset mode in `development.yaml` wires this).
- **Type conventions:** `i64` id/FK → TS `number` (`#[ts(type = "number")]`; JSON-ergonomic, accept
  >2^53 caveat); `Decimal` → `string` (`#[ts(type = "string")]`); `DateTime<Utc>` → `string`;
  `Option<T>` → `T | null`.
- **htmx/html server scaffolds removed; Tera retained for mailers.**

## Architecture

### 1. Backend (Loco / axum)

- **API controllers** under `src/controllers/posts.rs`: `list/get/create/update/remove`, each
  returning `Json<T>` (Loco `format::json`) under the `/api` prefix. JWT-guarded via the existing
  `auth::JWT` extractor; `list`/`get` may be public per app taste (reference: all guarded to exercise
  auth end-to-end).
- **DTOs** in `src/dtos/posts.rs`, distinct from sea-orm entities (entities stay DB-shaped; DTOs are
  the wire contract):
  - `PostDto` (response), `CreatePost`, `UpdatePost` (requests), each
    `#[derive(Serialize, Deserialize, TS)]` with `#[ts(export, export_to = "frontend/src/bindings/")]`
    (relative to the app crate root, which contains both `src/` and `frontend/`).
  - Shared value types (`PostStatus` enum, `Attachment` tagged enum, `Author`) derive `TS` too.
  - A generic `Page<T>` wrapper and an `ApiError { code, message, details }` envelope, both `TS`.
  - `From<entities::posts::Model> for PostDto` mapping (the one place DB shape → wire shape lives).
- **Bindings export step:** a dedicated cargo step regenerates `frontend/src/bindings/*.ts` from the
  DTOs. Validated mechanism: ts-rs emits per-type `export_bindings_*` tests; `cargo test` (with
  `TS_RS_EXPORT_DIR`/`export_to`) writes the files. Packaging as a test vs a `src/bin/export_bindings.rs`
  calling `export_all_to` is a plan-level detail; the reference will pick one and pin it. Bindings are
  **committed to VCS** (so the frontend typechecks without a Rust build) + a CI check asserts
  regeneration produces no diff (drift guard).

### 2. Frontend (Vite + React + react-router + TanStack Query)

```
frontend/
  vite.config.ts            # server.proxy: '/api' -> http://localhost:5150
  package.json              # react, react-dom, react-router, @tanstack/react-query, typescript, vite
  tsconfig.json
  src/
    main.tsx                # QueryClientProvider + RouterProvider
    bindings/               # GENERATED by ts-rs (committed)
    api/
      client.ts             # typed fetch wrapper (base url, auth header, error mapping)
      posts.ts              # TanStack Query hooks: useListPosts / usePost / useCreatePost / ...
    auth/
      token.ts              # token store (localStorage) + helpers
      RequireAuth.tsx       # route guard -> redirect to /login on missing/expired token
      Login.tsx             # login form -> POST /api/auth/login
    pages/posts/            # List.tsx / Show.tsx / New.tsx / Edit.tsx
    App.tsx                 # route table
```

- **`api/client.ts`** — thin wrapper over `fetch`: prefixes `/api` (relative; dev-proxied, prod
  same-origin), injects `Authorization: Bearer <token>`, parses JSON, and on non-2xx throws a typed
  error built from the `ApiError` binding. Generic `get<T>`, `post<TReq,TRes>`, `put`, `del`. On 401:
  clear token + redirect to `/login`.
- **`api/posts.ts`** — TanStack Query hooks importing types from `bindings/`:
  `useListPosts(query)` → `useQuery<Page<PostDto>>`; `useCreatePost()` → `useMutation<PostDto,
  ApiError, CreatePost>` with cache invalidation. This is the per-resource surface the generator will
  emit.
- **Pages** — react-router data-router pages using the hooks; forms typed by `CreatePost`/`UpdatePost`.

### 3. Auth flow

1. `Login.tsx` POSTs credentials → `/api/auth/login` (existing Loco JWT endpoint) → `{ token }`.
2. `token.ts` stores it (localStorage for the reference; note a memory+refresh upgrade path).
3. `client.ts` attaches `Authorization: Bearer`. `RequireAuth` gates protected routes.
4. 401 anywhere → clear token → redirect `/login`.

### 4. Dev / prod serving

- **Dev:** run Loco (`cargo loco start`, :5150) + `vite` (:5173). Vite proxies `/api` → :5150. Two
  processes (a unified `loco` dev command is a later nicety, out of scope here).
- **Prod:** `vite build` → `frontend/dist`; Loco serves it as static root with SPA fallback (config
  `asset: { kind: client, ... }`). Single origin, single binary path already proven by the existing
  clientside template.

## Error handling

- Server returns the `ApiError { code, message, details }` envelope on 4xx/5xx (align Loco's error
  responder to this shape). `client.ts` maps non-2xx → thrown `ApiError`; TanStack Query exposes it as
  `error`; a shared error UI (toast/boundary) renders `message`. Validation (422) `details` carries
  field errors for form display.

## Mapping to generator output (informs workstream 2, not built here)

- **Emitted once by `loco new`:** the whole `frontend/` scaffold (Vite, router, QueryClient,
  `api/client.ts`, `auth/`), the bindings export step, config, and the `dtos`/`controllers` module
  wiring.
- **Emitted per resource by `generate scaffold Post ...`:** `dtos/posts.rs` (with `#[derive(TS)]` +
  the type-convention attributes), `controllers/posts.rs`, `api/posts.ts` (Query hooks), and
  `pages/posts/*`. One typed column decision drives the Rust DTO field, its `ts(type=...)` override,
  the migration column, and the form input — the single-source-of-truth goal.

## Validation (definition of done for this workstream)

1. `cargo check` / `cargo clippy` clean on the backend.
2. Bindings export step produces `frontend/src/bindings/*.ts`; re-running yields no diff.
3. `tsc --noEmit` and `vite build` clean on the frontend.
4. Manual end-to-end smoke: log in → list posts → create a post (with an enum + a nullable field +
   the tagged-enum attachment) → see it in the list; a 401 with no token redirects to login.
5. Prod: `vite build` + `cargo loco start` serves the SPA and the API from one origin.

## Open questions for review

1. **Bindings in VCS + CI drift-check** (recommended) vs generated-on-prebuild (not committed)?
2. **react-router v7 data-router** confirmed? (merges Remix patterns; current mainstream.)
3. **Package manager** — pnpm (recommended) vs npm; and **Tailwind** — standalone CLI (Node-free
   build) vs classless/minimal CSS for the reference?
4. **Token storage** — localStorage (simple, reference default) vs httpOnly-cookie + refresh (more
   secure, more moving parts) — which should the *generated* default be?
5. **Auth endpoints** — reuse the existing Loco JWT login/register controllers as-is, or reshape them
   to the `ApiError` envelope + DTO conventions as part of this reference?
