## Evidence log

1. **FACT**: `src/testing/redaction.rs:15` defines `(r"password: (.*{60}),", "password: \"PASSWORD\",")`. Compiled and probed this regex directly against the `regex` crate (same crate pinned in `Cargo.toml:96`, used transitively by insta's `filters` feature, `Cargo.toml:217`): stacking `{60}` after an already-quantified `.*` does **not** constrain match length — it matches password fields of length 5, 30, 59, 60, 61, 65, and 100 identically (verified with a standalone `regex = "1"` probe program). → **Judgment**: this was almost certainly meant to require a fixed-length (bcrypt-style, 60-char) hash before redacting, but as written it's functionally `.*` — an inert length constraint shipped to every Loco user's snapshot tests, undetected because `redaction.rs` has no `#[cfg(test)]` module at all (confirmed: only `selector.rs` and `db.rs` have test modules). → **KPI 4, 6** → **Severity: High** (silent-wrong regex in a shipped user-facing redaction helper, zero test coverage).

2. **FACT**: `src/testing/request.rs:46-50` — `BootResultWrapper::drop` calls `self.test_db.cleanup_db()` synchronously (Drop can't be async). `src/testing/db.rs:109-127` — `PostgresTest::cleanup_db` responds by `tokio::task::spawn_blocking` a **new** `tokio::runtime::Runtime::new()` to run `DROP DATABASE`, and **does not await or join the resulting `JoinHandle`** — it's fire-and-forget. → **Judgment**: if the test process/thread exits shortly after the test body returns (the common case — most `#[tokio::test]` functions return immediately after their assertions), the background drop may never complete, leaking `_loco_test_*` databases in the target Postgres instance over repeated CI/test runs. → **KPI 4, 6** → **Severity: High**.

3. **FACT**: `src/testing/db.rs:246-249` (the crate's own unit test for this exact cleanup path) works around the async-drop race by doing `thread::sleep(time::Duration::from_secs(1))` before asserting the schema no longer exists. → **Judgment**: this is a textbook timing-dependent test — the very "ordering/timing assumptions" anti-pattern the rubric singles out — and it exists specifically because finding #2's fire-and-forget cleanup has no completion signal to await. The test papers over a real bug instead of proving the bug doesn't exist. → **KPI 4, 6** → **Severity: High**.

4. **FACT (git-verified)**: `git log -p -- src/testing/request.rs` shows commit `575f278d` (`refactor(testing)!: request helpers take impl AsyncFnOnce`, #1657) introduced `RequestConfig.default_scheme` (`request.rs:59,72,82,102-104`) but the `From<RequestConfig> for TestServerConfig` impl only forwarded `default_content_type`/`save_cookies` — `default_scheme` was silently dropped. It was only wired in by commit `f9b87a68` ("fix(1.0): correctness + doc-in-code fixes surfaced by the docs overhaul"), landing the line now at `src/testing/request.rs:130`. → **Judgment**: this is a real regression that shipped and lived across a release cycle before an unrelated docs pass caught it — precisely the "config-plumbing fragility" flagged in the audit brief. **Today there is still no test asserting the `From` conversion carries all `RequestConfig` fields through** (confirmed: `grep -rn "RequestConfig"` outside `request.rs` returns nothing; no test module exists in `request.rs` at all), so a repeat of this exact failure mode on the next new field is not guarded against. → **KPI 4, 6** → **Severity: High**.

5. **FACT**: `grep -rln "request_with_create_db\|request_config_with_create_db\|boot_test_with_create_db" tests/ src/` returns only `src/testing/request.rs` itself — these three public entry points (the DB-creating request/boot helpers, arguably the most complex code paths in the file, combining `BootResultWrapper`, `TestSupport::init_db`, and Drop-based cleanup) are never invoked by loco-rs's own test suite. Coverage of the DB-creation path comes only indirectly via `src/testing/db.rs:220-249`'s direct `PostgresTest`/`SqliteTest` unit tests, which bypass the `request_with_create_db` wrapper entirely. → **Judgment**: the harness's own most state-heavy public API is effectively untested end-to-end within the crate that ships it. → **KPI 6** → **Severity: Medium**.

6. **FACT**: `src/testing/db.rs:66-84` — `PostgresTest::new` builds `root_connection_string`/`connection_string` via `conn_str.replace(db_name, "postgres")` / `conn_str.replace(db_name, &test_schema_name)` — a naive substring replace on the whole connection URI, not a structured URL edit. `src/tests_cfg/config.rs` fixtures use short names like `test`/`test_custom` (`config.rs:97-101`) which would be low-risk, but any real-world `db_name` that also appears as a substring elsewhere in the URI (host, user, path segment) would corrupt the rewritten connection string silently. → **Judgment**: fragile string-typing on a security/connection-critical value. → **KPI 4** → **Severity: Low-Medium**.

7. **FACT**: `src/testing/db.rs:66-67,79,84,100,109-127` name the field `schema_name` and the variable `test_schema_name`, but `init_db` executes `CREATE DATABASE {schema_name}` (`db.rs:100`) and `cleanup_db` executes `drop database if exists {table_name}` (`db.rs:120`, where `table_name` is actually the same schema-named string) — i.e., this is full-database creation/teardown, not Postgres `CREATE SCHEMA` isolation, and one local variable is even mis-named `table_name` for what is a database name. → **Judgment**: three different, incorrect domain words (`schema_name`, `table_name` for what's really a `db_name`) for the same concept in ~20 lines — a maintainability/naming smell that will mislead the next contributor reasoning about isolation guarantees (e.g., whether tests share a single logical DB with schema-level isolation, vs. fully separate databases — they do the latter). → **KPI 5** → **Severity: Low**.

8. **FACT**: `src/testing/db.rs:173-175` — `SqliteTest::cleanup_db` does `std::fs::remove_dir_all(&self.db_folder).expect("Could not delete sqlite test db")`. This runs from `BootResultWrapper::drop` (`src/testing/request.rs:46-50`), which itself typically runs during unwind when a test assertion inside the `callback` has already panicked. → **Judgment**: if the temp dir is not removable (locked file handle, permissions, prior partial cleanup) at exactly the moment a test is already failing/unwinding, this `.expect()` triggers a second panic during the first panic's unwind, which Rust turns into a full process abort ("thread panicked while panicking") — destroying the original failing test's diagnostic output. Test-harness Drop paths should not panic. → **KPI 4** → **Severity: Medium**.

9. **FACT**: `src/testing/request.rs:174-182` (fence opens/closes cleanly) vs. `src/testing/request.rs:237-248` for `boot_test_unique_port`: the doc example opens a ` ```rust,ignore ` fence at line 237 with no matching closing ` ``` ` before the function definition at line 249 (confirmed via `grep -n '```' src/testing/request.rs`, showing an unpaired fence-open at 237 followed by the *next* function's fence-open at 289). The example body also ends with a literal `assert!(false)` placeholder (line 247) that was never replaced with a real assertion — the identical `assert!(false)` placeholder also appears in `src/testing/db.rs:32` for the `seed` doctest. → **Judgment**: copy-pasted, never-finished rustdoc examples shipped in the public API docs of the harness; harmless only because the fences are `rust,ignore` (never compiled). → **KPI 1** → **Severity: Low**.

10. **FACT**: `src/testing/selector.rs` repeats `let document = Html::parse_document(html); let parsed_selector = Selector::parse(selector).unwrap();` verbatim at the top of 8 of its 9 public functions (`selector.rs:25-26, 55-56, 85-86, 156-157, 199-200, 246-247, 284-285, 323-324`). → **Judgment**: straightforward extractable duplication (a private `fn elements<'a>(html: &'a str, selector: &str) -> impl Iterator<Item=ElementRef<'a>>` would remove ~14 duplicated lines and centralize the `.unwrap()` panic message for bad selectors). → **KPI 2, 3** → **Severity: Low**.

11. **FACT**: The API surface for booting a test app is 4 near-orthogonal entry points — `request`/`request_with_create_db`/`request_with_config`/`request_config_with_create_db` (`request.rs:303,328,348,374`) plus 3 boot variants (`boot_test`, `boot_test_with_create_db`, `boot_test_unique_port`, `request.rs:186,210,249`) — but the axes don't fully cross: there is no way to combine `boot_test_unique_port` with DB-creation or with a custom `RequestConfig`. → **Judgment**: organic, non-orthogonal growth of the entry-point matrix (each combination added on demand rather than designed as a single builder) — a mild KPI1 smell, though not yet painful at 2×2 scale. → **KPI 1, 2** → **Severity: Low**.

## Patch-on-patch smells

- `src/testing/request.rs:130` — `default_scheme` forwarding fix, landed only in the `1.0` docs-overhaul correctness pass (`f9b87a68`) after shipping broken since `575f278d`; still no regression test (evidence log #4).
- `src/testing/request.rs:247` and `src/testing/db.rs:32` — duplicated unfinished `assert!(false)` doc-example placeholders (evidence log #9).
- `src/testing/request.rs:237-248` — unterminated markdown code fence in a public rustdoc example (evidence log #9).
- `src/testing/db.rs:246-249` — `thread::sleep(1s)` timing workaround standing in for a real async-completion signal on DB cleanup (evidence log #3).
- Four `#[allow(clippy::future_not_send)]` suppressions clustered in one file (`src/testing/request.rs:259,302,326,372`) — justified (test-harness futures are intentionally single-threaded) but is exactly the repeated-suppression pattern the audit brief asks to flag; low severity since it's a deliberate, consistent choice rather than ad hoc patching.

## Library hypotheses

1. **HYPOTHESIS**: `src/testing/request.rs:69-122` (`RequestConfigBuilder`, hand-rolled builder for a 3-field struct, ~50 LOC) could be replaced by `#[derive(bon::Builder)]` or `derive_builder`. **Why it might be simpler**: removes ~40 lines of manual builder boilerplate. **Risk / why it might not fit**: adds a proc-macro dependency + compile-time cost for a struct this small and stable; Loco is deliberately lean and this builder is unlikely to grow much. **NEEDS SPIKE**, but low priority — likely not worth it.

2. **HYPOTHESIS**: `src/testing/db.rs:109-127` (fire-and-forget `spawn_blocking` + fresh `tokio::runtime::Runtime` for async cleanup from a sync `Drop`) could use a crate purpose-built for "async cleanup on drop," e.g. `async-dropper`, or more simply restructure `BootResultWrapper` to expose an explicit async `close()`/`cleanup()` that test authors (or an internal `#[tokio::test]`-aware macro) call before drop, falling back to best-effort sync cleanup only as a safety net. **Why it might be simpler/safer**: removes the double-runtime-per-drop cost and the unawaited leak risk found in evidence log #2. **Risk**: any explicit-close API is opt-in and can still be skipped by users (same class of problem, just documented instead of silent); a full async-Drop crate is still an unstable/awkward area in Rust today. **NEEDS SPIKE**.

3. **HYPOTHESIS**: `src/tests_cfg/postgres.rs:40-72` and `src/tests_cfg/redis.rs:35-64` hand-roll near-identical "retry connect up to 10× with 1s sleep" polling loops around `testcontainers`. `testcontainers`' own `WaitFor` / readiness-probe mechanisms (already partially used, e.g. `WaitFor::message_on_stdout`) or the `backon`/`tokio-retry` crates could replace the duplicated manual retry loop. **Why it might be simpler**: removes ~25 duplicated lines across two files. **Risk**: `WaitFor::message_on_stdout` already gates container start; the extra manual retry loop may be compensating for a real gap (log-message readiness firing before the port actually accepts connections), so removing it needs care. **NEEDS SPIKE**.

## What is genuinely excellent (cited)

- `src/testing/db.rs:44-52` (`init_test_db_creation`) plus the `TestSupport` trait (`db.rs:54-61`) is a clean, minimal strategy abstraction — one trait, three small impls, dispatched by URI prefix. Exactly the "just enough things to model the domain" the rubric rewards.
- `src/testing/selector.rs` test module (`selector.rs:332-573`) is a real positive: every public assertion helper has both a passing-path and a `catch_unwind`-verified panic-message test, which is uncommonly thorough for a small helper file.
- `src/tests_cfg/config.rs:12-63` (`test_config()`) is the **sole** place in the whole crate that constructs a full `Config` struct literal (`grep -rn "config::Config {" src/` outside `tests_cfg` returns nothing) — good single-source-of-truth economy, and because `Config` does not derive `Default`, the compiler forces this function to be updated whenever a field is added (unlike the `TestServerConfig` conversion in evidence log #4, which uses `..Default::default()` and can silently swallow new fields).
- `src/testing/redaction.rs`'s `cleanup_user_model`/`cleanup_email` composition (`redaction.rs:89-102`) is a tidy, minimal way to let app authors compose category-specific regex filter sets for insta snapshots without writing regexes themselves — good ergonomic design, undermined only by the untested regex bug in evidence log #1.

## Top 3 things that would most raise the area's quality

1. Fix the async-Drop cleanup race (evidence log #2, #3, #8): give `BootResultWrapper`/`TestSupport` an explicit awaited async cleanup path (or at minimum `join` the `spawn_blocking` handle and make `SqliteTest::cleanup_db` non-panicking), and delete the `thread::sleep(1s)` test in favor of asserting on the actual completion future.
2. Add a unit test asserting `From<RequestConfig> for TestServerConfig` forwards every field (evidence log #4) — this is the cheapest possible guard against the exact regression that already shipped once, and add a test for `redaction.rs`'s regexes actually matching their intended shapes (evidence log #1), since the current password regex is provably inert.
3. Land at least one crate-internal test that exercises `request_with_create_db`/`request_config_with_create_db` end-to-end (evidence log #5), not just the underlying `PostgresTest`/`SqliteTest` primitives — the wrapper composition (boot + db-create + Drop cleanup) is the part users actually call and is currently the least-tested layer.
