# Area: A5 · Background Workers & Queues

## Scope (files reviewed, with LOC)
- `src/bgworker/mod.rs` (889) — `Queue` enum (Redis/Postgres/Sqlite/None), `BackgroundWorker` trait, `create_queue_provider`, `converge`.
- `src/bgworker/sql.rs` (245) — **shared** SQL-backend primitives: `Job`, `RunOpts`, `Driver` trait, `JobRegistry` (register + poll/dispatch/retry loop). Used by both `pg.rs` and `sqlt.rs`.
- `src/bgworker/pg.rs` (1246) — Postgres backend: connect/init/enqueue/dequeue/complete/fail/cancel/clear/requeue/get_jobs + 17 `#[tokio::test]`s (via testcontainers).
- `src/bgworker/sqlt.rs` (1466) — SQLite backend: same operation set, own lock-table for mutual exclusion + 17 tests.
- `src/bgworker/redis.rs` (1800) — Redis backend: **own** `Job`, `JobHandler`, `JobRegistry` (register + poll loop) duplicated from `sql.rs` rather than implementing `Driver`; ZSET-based priority queue + Lua claim script + 18 tests (via testcontainers).

Total 5,646 LOC. All files read in full.

## Evidence log

1. **FACT**: `to_job()` in `pg.rs:456-488` and `to_job()` in `sqlt.rs:525-557` are line-for-line identical logic (same field extraction, same tag-JSON-array unwrap-to-`None`-if-empty logic, same error path), differing only in the row type (`PgRow` vs `SqliteRow`). → **Judgment**: this is copy-paste that a shared generic `fn to_job<R: Row>(row: &R) -> Result<Job>` (using `sqlx::Row` bound methods, which are dialect-agnostic for these column types) could collapse to one function. → **KPI 2, 3**. Severity: **medium** (pure duplication, zero behavioral divergence).

2. **FACT**: `enqueue()` bodies in `pg.rs:128-161` and `sqlt.rs:121-155` are ~90% identical (same param list, same `Ulid::new()`, same tags-to-JSON, same interval-to-ms cast, same debug log) — the only dialect difference is `sqlt.rs:143` wrapping `run_at` in `DATETIME($4)`. Likewise `fail_job()` (`pg.rs:257-271` vs `sqlt.rs:293-307`) differs only in `task_data || $2::jsonb` (Postgres) vs `json_patch(task_data, $2)` (SQLite), and `cancel_jobs_by_name()` (`pg.rs:282-293` vs `sqlt.rs:318-330`) and `ping()` (`pg.rs:399-405` vs `sqlt.rs:444-450`) are identical modulo table name. → **Judgment**: real, quantifiable copy-paste; the `Driver` trait (`sql.rs:61-82`) proves the authors already accepted a "small dialect-specific core, shared everything else" architecture for `dequeue`/`complete_job`/`fail_job` — but stopped short of applying it to `enqueue`/`cancel_jobs_by_name`/`ping`/`to_job`/`connect`/`create_provider`, which are equally dialect-thin. → **KPI 1, 3**. Severity: **medium-high** (this is the "known suspect" pattern, precisely quantified).

3. **FACT**: `dequeue()` genuinely differs by dialect and is **correctly not** shared: Postgres uses `SELECT ... FOR UPDATE SKIP LOCKED` inside a transaction for row-level concurrency safety (`pg.rs:163-225`), while SQLite (no `SKIP LOCKED` support) uses an explicit single-row mutex table `sqlt_loco_queue_lock` acquired/released within the same transaction (`sqlt.rs:157-260`, table created at `sqlt.rs:83-89`). Tag filtering also differs by dialect: Postgres `(tags)::jsonb ? $n` (`pg.rs:184-192`) vs SQLite `json_extract(tags,'$') LIKE ?` (`sqlt.rs:193-204`). → **Judgment**: this asymmetry is **justified** — genuinely different SQL capabilities, and forcing a shared implementation here would add worse coupling (fair per rubric's "be fair" clause). → **No KPI penalty**; noted as the "good" duplication baseline against which Evidence #1/#2 should be judged.

4. **FACT**: `Job` struct is defined twice with identical fields/derives: `sql.rs:36-50` (shared by pg+sqlt) and `redis.rs:36-50` (redis-only). `JobHandler` type alias is defined twice, byte-identical apart from visibility: `sql.rs:27-34` (`pub(crate)`) vs `redis.rs:27-34` (private). `JobRegistry::register_worker` — the panic-catching wrapper — is duplicated near-verbatim including comments and variable names: `sql.rs:100-137` vs `redis.rs:99-134` (`AssertUnwindSafe(w.perform(args)).catch_unwind()`, same `panic_msg` downcast chain, same `"worker panicked"` log). → **Judgment**: `redis.rs` could have implemented the `Driver` trait (extended with an associated "ack context" type to carry `queue_name`, needed for Redis's processing-set bookkeeping) and reused `sql::JobRegistry` wholesale instead of re-deriving the same struct/registry/loop shape. This is the single largest concrete duplication in the area (~150 LOC of registry/loop machinery, plus the `Job` struct). → **KPI 1, 2, 3, 5**. Severity: **high**.

5. **FACT**: `redis.rs:971` — `create_provider()` calls `tokio::time::sleep(std::time::Duration::from_secs(3)).await;` unconditionally, with no comment, no config flag, immediately before returning `Queue::Redis(...)`. No equivalent sleep exists in `pg::create_provider` (`pg.rs:495-513`) or `sqlt::create_provider` (`sqlt.rs:457-475`). → **Judgment**: looks like an undocumented workaround (possibly for Redis connection/cluster warm-up) that silently adds 3s to every app boot when the Redis queue backend is configured, with no way to disable or understand it from the code. → **KPI 1, 4**. Severity: **high** (brittle, unexplained, boot-time cost, and it's inconsistent — no other backend needs it).

6. **FACT**: `RedisQueueConfig` (`src/config/queue.rs:17-28`) has no `poll_interval_sec`, `connect_timeout`, `idle_timeout`, `max_connections`/`min_connections`, or `enable_logging` fields, unlike `PostgresQueueConfig`/`SqliteQueueConfig` (`src/config/queue.rs:30-86`) which expose all of these with shared defaults (`pgq_poll_interval`/`sqlt_poll_interval` at `src/config/queue.rs:88-94`). Redis's poll interval is hardcoded to `1` at `redis.rs:963`. → **Judgment**: the same domain concept (queue polling cadence, connection tuning) is modeled inconsistently across the three backends for no stated reason. → **KPI 1, 5**. Severity: **medium**.

7. **FACT**: No automatic requeue/visibility-timeout mechanism exists in any backend's poll loop (`sql.rs:147-238` for pg/sqlt; `redis.rs:144-229` for redis) — `requeue()` (`pg.rs:377-392`, `sqlt.rs:386-399`, `redis.rs:786-879`) is only invoked from the CLI: `cli.rs:1291: JobsCommands::Requeue { from_age } => queue.requeue(from_age).await`. Grep confirms no scheduler/cron call site (`grep -rn requeue src/scheduler.rs src/task.rs` → no matches). → **Judgment**: a worker process crash leaves a job stuck in `Processing` indefinitely unless an operator manually runs `cargo loco jobs requeue`; this is a shared correctness/operability gap across all three backends, not a duplication issue. → **KPI 6**. Severity: **medium-high** (production reliability gap).

8. **FACT**: Test suites for `pg.rs` (17 tests, `pg.rs:515-1247`) and `sqlt.rs` (17 tests, `sqlt.rs:559-1467`) test the identical behavior list (`can_enqueue`, `can_dequeue`, `can_complete_job_without_interval`/`with_interval`, `can_fail_job`, `can_cancel_job_by_name`, `can_clear`, `can_clear_by_status`, `can_clear_jobs_older_than[_with_status]`, `can_get_jobs[_with_age]`, `can_requeue`, `can_dequeue_with_priority_*`, `can_handle_worker_panic`, `can_dequeue_with_tags`) via copy-pasted-and-adapted test bodies. None of these tests spins up 2+ concurrent worker tasks racing to dequeue the same row set — the closest is `can_handle_worker_panic` / `test_job_registry_redis`, which run exactly 1 worker. → **Judgment**: good behavioral coverage per backend, but the tests never actually prove the concurrency-safety claim (`SKIP LOCKED` / lock-table / Lua script) under real contention. → **KPI 6**. Severity: **medium**.

## Patch-on-patch smells (specific, cited)
- Unexplained 3-second unconditional sleep, no comment, no flag: `redis.rs:971` (Evidence #5).
- Silent, undocumented scan cap `MAX_SEARCH: isize = 1000` in tag-filtered Redis dequeue: `redis.rs:335-336` used at `redis.rs:348`.
- Auto-migration shims bolted onto `initialize_database` for both SQL backends — "add column if missing" logic added after the fact for a schema change: `pg.rs:80-97` ("Auto-migrate: add the priority column to pre-existing tables"), `sqlt.rs:97-111` ("Auto-migrate: add the priority column to pre-existing databases") — duplicated shim logic, not centralized even though both are the identical migration.
- No `TODO`/`FIXME`/`HACK` comments and no `_archive`/dead code found in `src/bgworker/` (`grep -n "TODO\|FIXME\|HACK\|XXX" src/bgworker/*.rs` → no matches) — genuinely clean on this axis.
- `#[allow(unused_variables)]` on `Queue::enqueue`/`register`/`run` (`mod.rs:108,161,196`) and `#[allow(dead_code)]` on `process_worker_handles` (`mod.rs:241`) exist purely to paper over the `#[cfg(feature=...)]`-gated match arms when only a subset of backend features are compiled — a structural side effect of the 3-backend-behind-cfg design, not hidden bugs, but a small "suppression smell" worth naming.

## Library hypotheses
- **Hand-rolled code**: the entire poll/dequeue/ack/retry loop across `sql.rs:147-238` + `redis.rs:144-229`, ~5,646 LOC total. **Candidate**: `apalis` (multi-backend async job-processing framework with `apalis-sql` (Postgres/SQLite/MySQL) and `apalis-redis` backends, built-in retry/backoff, cron). **Why it MIGHT be simpler**: it already solves "one `Storage`/`Backend` trait, N backends," which is exactly the gap identified in Evidence #4 — Loco is hand-rolling what apalis productizes. **Risk / why it might NOT fit**: Loco's queue has bespoke features not obviously mapped to apalis's model — full-range `i32` priority with explicit tie-break semantics (`pg.rs:104-107` in `mod.rs`'s enqueue doc), tag-based worker routing (`dequeue` tag filters in all 3 backends), YAML dump/import (`mod.rs:519-605`), and admin ops (`clear_jobs_older_than`, `clear_by_status`, `cancel_jobs_by_name`) — adopting it would mean either extending apalis or re-implementing these on top of it, which could net out to *more* code, not less, plus a new dependency surface for a framework that positions itself as lean. **NEEDS SPIKE**.
- **Hand-rolled code**: Redis Lua-script atomic claim + manual ZSET/SET/SADD bookkeeping (`redis.rs:310-433`). **Candidate**: none identified that is *simpler* — dedicated Redis queue crates (e.g., an RSMQ-style library) exist but would still require the same custom priority/tag semantics Loco has now; not flagged as a real candidate. **NEEDS SPIKE only if** priority/tag requirements are relaxed.

## What is genuinely excellent (cited — be specific)
- `sql.rs:1-7` doc comment explicitly states the module's purpose and rationale ("This module holds the code that is identical between... Each backend supplies its own pool type and the three DB-coupled operations... through the Driver trait") — this is a rare case in the codebase of the *intent* behind an abstraction being written down, and the abstraction genuinely holds (`sql.rs:61-82` `Driver` trait, `sql.rs:147-238` shared `run()`).
- Priority-ordering correctness is well thought through and *documented*: `mod.rs:104-107` states the exact tie-break semantics ("Ties are resolved by earlier `run_at`, then by stable job id ordering"), and `redis.rs:299-308` explains *why* the ZSET score uses priority alone rather than a combined priority+timestamp score (to avoid precision loss across the full `i32` range) — this is exactly the kind of subtle correctness reasoning that's easy to get wrong, and it's both correct and explained.
- Concurrency-safety mechanisms are backend-appropriate, not cargo-culted: Postgres uses native `FOR UPDATE SKIP LOCKED` (`pg.rs:195`), SQLite (lacking that) uses an explicit lock-table serialized through a transaction (`sqlt.rs:160-174`), Redis uses an atomic Lua claim script (`redis.rs:310-323`) — three different, each individually correct, solutions to the same "don't double-process a job" problem, matched to what each store actually offers (Evidence #3's "good duplication").
- Panic isolation: worker panics are caught via `AssertUnwindSafe(...).catch_unwind()` and turned into a normal `fail_job` outcome rather than crashing the poll loop (`sql.rs:113-126`, `redis.rs:112-124`), and this is actually tested end-to-end per backend (`pg.rs:1045-1107 can_handle_worker_panic`, `sqlt.rs:1251-1318`, redis via `test_job_registry_redis`).
- Test realism: all three backends are tested against real engines via `testcontainers` (not mocks) — `pg.rs:572-587 setup_pg_test`, `sqlt.rs` uses real sqlite files via `tree_fs`, `redis.rs:987-991 setup_redis` — giving genuine confidence in SQL/Lua correctness rather than happy-path unit stubs.

## Top 3 things that would most raise the area's quality
1. Fold `redis.rs`'s `Job`/`JobHandler`/`JobRegistry`/register/run-loop (Evidence #4, ~150+ LOC) into the `sql.rs` abstraction by extending `Driver` with an associated ack-context type (to carry Redis's `queue_name`), eliminating the second parallel implementation of the exact same conceptual loop.
2. Extend the `Driver`-style trait to also cover the ~300 LOC of dialect-thin duplication in `enqueue`/`fail_job`/`cancel_jobs_by_name`/`ping`/`to_job`/`connect` between `pg.rs` and `sqlt.rs` (Evidence #1, #2) — e.g. a small `Dialect` trait supplying just the differing SQL fragments (timestamp fn, jsonb-merge operator, placeholder style), with the row-mapping and query shape shared once.
3. Add an automatic visibility-timeout reaper (a periodic requeue-stale-jobs pass inside each backend's own poll loop, or a documented recommendation to wire `Queue::requeue` into the scheduler) so crash recovery doesn't depend on an operator remembering to run `cargo loco jobs requeue` (Evidence #7) — and delete/explain the unconditional 3s sleep in `redis::create_provider` (Evidence #5), which currently reads as an undiagnosed patch.
