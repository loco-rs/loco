## Evidence log

1. **FACT**: `JWTWithUser::from_request_parts` (`src/controller/extractor/auth.rs:67-99`) and the free function `extract_jwt_from_request_parts` (`src/controller/extractor/auth.rs:126-146`) both execute the identical sequence: `AppContext::from_ref` → `extract_token(get_jwt_from_config(&ctx)?, parts)` → `ctx.config.get_jwt_config()?` → `auth::jwt::JWT::new(&jwt_secret.secret).validate(&token)` → identical `Ok`/`Err` handling (`Error::Unauthorized("token is not valid")` on error). **Judgment**: `JWTWithUser` should call `extract_jwt_from_request_parts` and then do the extra `T::find_by_claims_key` lookup, instead of re-implementing token extraction+validation. **KPI**: 1, 2, 3. **Severity**: Medium (correctness risk if one path is patched and the other isn't — already an early sign here, see #2).

2. **FACT**: Within the duplicated logic from #1, two *different* accessor functions are called back-to-back for the same config value: `get_jwt_from_config(&ctx)` (`src/controller/extractor/auth.rs:152-160`, defined in this file) returns `&JWTConfig` by walking `ctx.config.auth.as_ref()...jwt.as_ref()`, then two lines later `ctx.config.get_jwt_config()` (`src/config/mod.rs:180-188`, a *different* implementation) walks the exact same `self.auth.as_ref().and_then(|auth| auth.jwt.as_ref())` path again — same data, two hand-written traversals with different error messages (`"JWT token not configured"` vs `"no JWT config found"`). **Judgment**: The first call's returned reference already contains `.secret`; the second call is pure redundant re-derivation and a second place that must be kept in sync with `Auth`'s shape. **KPI**: 1, 2, 7 (config.rs already provides the abstraction; auth.rs re-invents a second one). **Severity**: Low-Medium (correctness-safe today, but a maintenance/drift smell, and it's cross-crate-boundary duplication — auth.rs is A8, `Config::get_jwt_config` is A9).

3. **FACT**: `extract_token_from_cookie` (`src/controller/extractor/auth.rs:224-234`) does: `jar.get(name)` → `.to_string()` (renders `Cookie`'s `Display`, i.e. `"name=value"`) → `.strip_prefix(&format!("{name}="))` → `.to_string()`. `axum_extra::extract::cookie::Cookie` already exposes `.value() -> &str` directly. **Judgment**: this is hand-rolled string reparsing of something the cookie crate gives for free; it happens to be correct today only because request-parsed cookies carry no attributes, but it's needlessly fragile (relies on `Display` format staying `name=value` forever) compared to calling `.value()`. **KPI**: 4, 7. **Severity**: Low (works correctly now, but is the kind of "why is this here" code the audit is meant to flag).

4. **FACT**: `JWT::algorithm()` (`src/auth/jwt.rs:49-54`) lets a caller override `self.algorithm` to any `jsonwebtoken::Algorithm`, including asymmetric ones (RS256/ES256/etc). But `generate_token` (`src/auth/jwt.rs:83`) always builds keys via `EncodingKey::from_base64_secret(&self.secret)` and `validate` (`src/auth/jwt.rs:108`) always builds `DecodingKey::from_base64_secret(&self.secret)` — both symmetric-secret-only constructors. **Judgment**: the builder advertises algorithm flexibility that cannot actually work for the asymmetric half of the `Algorithm` enum (it will error at encode/decode time with a confusing key-format error, not a clear "unsupported" message), and there is no test exercising `.algorithm(...)` at all. This is a partially-built, unused escape hatch — a "concept" that doesn't fully exist. **KPI**: 1, 4, 6. **Severity**: Medium (latent footgun for any user who discovers and tries this public API).

5. **FACT**: `ModelError` match arms are duplicated near-verbatim in `JWTWithUser::from_request_parts` (`src/controller/extractor/auth.rs:78-88`, log text `"Database error during authentication"` / `"Authentication error"`) and in `ApiToken::from_request_parts` (`src/controller/extractor/auth.rs:283-293`, log text `"Database error during API key authentication"` / `"API key authentication error"`) — identical structure (`EntityNotFound` → `Unauthorized("not found")`, `DbErr` → log + `InternalServerError`, `_` → log + `Unauthorized("could not authorize")`), differing only in log message wording. **Judgment**: a shared helper `fn map_model_err(e: ModelError, context: &str) -> Error` would remove this duplication. **KPI**: 2, 3. **Severity**: Low.

6. **FACT**: `validate.rs` defines 6 nearly identical `FromRequest` impls — `JsonValidateWithMessage`/`JsonValidate` (`:40-55`, `:131-149`), `FormValidateWithMessage`/`FormValidate` (`:85-100`, `:179-197`), `QueryValidateWithMessage`/`QueryValidate` (`:227-244`, `:275-295`) — each differing only in (a) which axum extractor (`Json`/`Form`/`Query`) is used and (b) whether a validation failure returns `Error::Validation(err)` (detailed) or `Error::BadRequest(String::new())` (generic, with a `tracing::debug!` line). **Judgment**: this is a textbook 3×2 matrix that a single generic wrapper (`Validated<E, T, const DETAILED: bool>`-style, or two small macros) would collapse to a fraction of the LOC without losing the public API shape. **KPI**: 2, 3, 7 (this is close to what `axum-valid` already generalizes). **Severity**: Low-Medium (pure maintenance cost, not a bug — but every new extractor kind repeats the pattern a 7th time).

7. **FACT**: `Validation::new(self.algorithm)` sets `validate.leeway = 0` (`src/auth/jwt.rs:103-104`), i.e. zero clock-skew tolerance on `exp` checking, and there is no test asserting behavior at the exact expiry boundary (the existing "token expired" test case uses a 1s expiration + 3s sleep, `src/auth/jwt.rs:125,147`, which is far past any boundary condition, not an edge-case test). **Judgment**: reasonable default for a single-process framework, but in any multi-node deployment with imperfect NTP sync this will reject tokens that a 5-30s leeway would accept — worth documenting as a deliberate choice since it's invisible from the config surface (`config/auth.rs` exposes no leeway knob). **KPI**: 4, 6. **Severity**: Low (design choice, not a bug, but untested and unconfigurable).

8. **FACT**: `TOKEN_PREFIX: &str = "Bearer "` (`src/controller/extractor/auth.rs:45`) is matched via exact `strip_prefix` (`:214`), which is case-sensitive. RFC 6750/7235 treat the auth-scheme token as case-insensitive, so a spec-conformant client sending `bearer <token>` (lowercase) would be rejected with "error strip authorization value" rather than accepted. No test covers a lowercase scheme. **Judgment**: minor interop/correctness gap. **KPI**: 6. **Severity**: Low.

## Patch-on-patch smells

- Two parallel JWT validate-and-extract code paths that must be kept in sync by hand (`src/controller/extractor/auth.rs:67-99` vs `:126-146` — see Evidence #1).
- Duplicate JWT-config accessor logic living in two different modules/crates-areas (`src/controller/extractor/auth.rs:152-160` vs `src/config/mod.rs:180-188` — see Evidence #2).
- Copy-pasted `ModelError`-to-`Error` mapping (`src/controller/extractor/auth.rs:78-88` and `:283-293` — see Evidence #5).
- Copy-pasted extractor scaffolding across `validate.rs`'s 6 structs (`src/controller/extractor/validate.rs:40-295` — see Evidence #6); every new "validate this axum extractor" need repeats ~15 lines of `FromRequest` boilerplate.
- No `#[allow(...)]`, no `TODO`/`FIXME`/`HACK`, no dead/commented-out code, no `_archive` found in this area — notably clean on that axis.

## Library hypotheses

1. **HYPOTHESIS**: `validate.rs`'s 6 near-identical `FromRequest` impls (`src/controller/extractor/validate.rs:40-295`, Evidence #6) could be replaced or generated by the `axum-valid` crate, which provides a generic `Valid<E>` wrapper over any axum body extractor (`Valid<Json<T>>`, `Valid<Form<T>>`, `Valid<Query<T>>`) plus a `ValidRejection` error hook. **Why it might be simpler**: collapses ~255 LOC of hand-written impls to a handful of type aliases/trait-impls. **Risk / why it might not fit**: Loco's two-tier error contract (detailed `Error::Validation` with per-field JSON vs generic `Error::BadRequest(String::new())`) is a custom shape that `axum-valid`'s single rejection type may not reproduce exactly without a custom `IntoResponse`/rejection adapter, and it's an additional dependency for what is currently working, tested code. **NEEDS SPIKE**.

2. **HYPOTHESIS**: `extract_token_from_cookie`'s manual `.to_string()` + `strip_prefix` round-trip (`src/controller/extractor/auth.rs:224-234`, Evidence #3) should just call `Cookie::value()` from the already-imported `axum_extra::extract::cookie` — this isn't a new dependency, just using more of the one already in use. **Why it's simpler**: removes a fragile format-dependent string operation for a direct accessor. **Risk**: essentially none; this is a same-crate API already available. **NEEDS SPIKE** (trivial one, but per rubric still flagged as hypothesis not asserted).

3. **HYPOTHESIS (considered and rejected)**: `garde` as a `validator` replacement for `validation.rs`. **Why it might seem simpler**: `garde` has a more modern derive API and built-in `Report` structure similar to `ModelValidationErrors`. **Risk / why it likely does NOT fit**: Loco already has a working `validator` integration (`src/validation.rs:147-151`) plus a from-scratch adapter trait (`ValidatorTrait`) that lets *any* validation approach (not just `validator`-derived types) plug in (proven by the `CustomData`/`CustomValidator` tests in `src/controller/extractor/validate.rs:585-621` and `src/validation.rs:200-222`) — switching crates would not reduce LOC and would break the existing adapter contract for zero benefit. **NEEDS SPIKE** only if `validator` itself becomes unmaintained; not recommended now.

## What is genuinely excellent (cited)

- **Fixed JWT algorithm eliminates alg-confusion entirely**: `JWT_ALGORITHM: Algorithm = Algorithm::HS512` (`src/auth/jwt.rs:13`) is baked into every `JWT::new(...)`, and `Validation::new(self.algorithm)` (`src/auth/jwt.rs:103`) means `decode()` will reject any token whose header `alg` doesn't match — a real, tested defense (see the "valid token"/"token expired" snapshot suite, `src/auth/jwt.rs:123-153`) against the classic "alg:none"/algorithm-substitution JWT attack class, achieved simply by not exposing algorithm choice through config at all.
- **`hash.rs` is a model "thin wrapper"**: `hash_password`/`verify_password` (`src/hash.rs:21-58`) do nothing but construct `Argon2` with explicit `Argon2id`/`V0x13` and delegate everything else (salting, constant-time comparison, per-hash parameter re-derivation on verify) to the `argon2`/`password-hash` crates. Verified against the vendored crate source that `Params::default()` (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/argon2-0.5.3/src/params.rs:42,52,61`) equals `m_cost=19456 (19 MiB), t_cost=2, p_cost=1` — i.e. matches OWASP's first-choice Argon2id recommendation out of the box, with zero custom tuning logic to get wrong.
- **Multi-location JWT extraction is a clean small state machine, not string-typed special-casing**: `get_jwt_locations`/`extract_token_from_location`/`extract_token` (`src/controller/extractor/auth.rs:167-247`) model "try these locations in order" as a `Vec<&JWTLocation>` + `match`, not nested ifs, and it's exhaustively tested for single/multiple/fallback/all-fail cases (`src/controller/extractor/auth.rs:496-859`, ~20 dedicated test functions) — this is likely *why* auth.rs is 860 LOC, and it's LOC well spent on real edge-case coverage, not padding.
- **Every public function in this area has a runnable doc example** (`src/auth/jwt.rs:27-32,63-69,97-101`, `src/hash.rs:15-20,41-46,62-71`) — consistent, disciplined API documentation across the whole area.

## Top 3 things that would most raise the area's quality

1. Collapse the two parallel JWT extract-and-validate paths (`JWTWithUser::from_request_parts` and `extract_jwt_from_request_parts`, `src/controller/extractor/auth.rs:67-99` / `:126-146`) into one, and make `JWTWithUser` call the free function — removes the biggest duplication risk in the file (Evidence #1, #2).
2. Collapse `validate.rs`'s 6 near-identical extractor structs (`:40-295`) into one generic implementation parameterized over the inner axum extractor and the error-detail mode — cuts ~150+ LOC of boilerplate without losing the public API (Evidence #6).
3. Either wire up `JWT::algorithm()` to actually support asymmetric keys (accepting `EncodingKey`/`DecodingKey` directly instead of always deriving from a base64 secret) or remove the builder method — right now it's a public API that silently doesn't work for half its own input domain (Evidence #4).
