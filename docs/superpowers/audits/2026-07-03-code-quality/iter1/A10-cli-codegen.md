## Evidence log

1. **FACT**: `src/cli.rs:712-869` (`main<H,M>`, with-db) and `src/cli.rs:872-1015` (`main<H>`, no-db) are two independent copies of the same command-dispatch `match cli.command { ... }` block — `Start`, `Routes`, `Middleware`, `Task`, `Scheduler`, `Generate`, `Doctor`, `Version`, `Watch` arms are duplicated verbatim (only `Db`/`Jobs` differ by cfg-gating). → **Judgment**: this is the single largest duplication in the area; every future `Commands` variant must be hand-added to both functions or they silently diverge. → **KPI 1, 3, 5**. Severity: **High**.
2. **FACT**: `loco-gen/src/scaffold.rs:24-75` re-implements the exact `match field_type { Reference | ReferenceWithCustomField | NullableReference | NullableReferenceWithCustomField | Type | TypeWithParameters }` walk that `loco-gen/src/model.rs:36-95` (`get_columns_and_references`) already performs, just resolving `rust_field`/`rust_field_with_params` instead of `col_type_field`. → **Judgment**: two parsers over the same `FieldType` enum, each hardcoding reference-field handling (`"i32"`/`"Integer"`/`"IntegerNull"` literals in `scaffold.rs:38,41,45,48-52` bypass `mappings.json` entirely, unlike the migration/model path). A shared helper returning `(col_type, rust_type)` pairs would remove one whole copy. → **KPI 2, 3**. Severity: **Medium-High**.
3. **FACT**: `loco-gen/src/templates/scaffold/html/view.t` and `loco-gen/src/templates/scaffold/htmx/view.t` are 100% identical (`diff` produces no output). `view_list.t`/`view_create.t`/`view_edit.t`/`view_show.t` differ only in HTMX form attributes and a handful of lines (verified with `diff`, e.g. htmx swaps `<form action=... method="post">` for `hx-post=...`). None of the ~40 `.t` files use Tera's `{% include %}`/`{% extends %}` to share the common 80-90% (grep for `extends`/`include` across `loco-gen/src/templates/` only matches unrelated `view_edit.t`/`view_create.t` occurrences of the literal word, not the tag). → **Judgment**: ~900 LOC of near-duplicate HTML/HTMX view templates (`loco-gen/src/templates/scaffold/{html,htmx}/*.t`) that could be built from one Tera base + a `is_htmx` flag. → **KPI 2, 3**. Severity: **Medium**.
4. **FACT**: `loco-gen/src/mappings.json` has 69 `name` rows (`grep -c '"name":'`), of which the `int`/`int!`/`int^` entries (lines 111-127) are byte-for-byte identical to `big_int`/`big_int!`/`big_int^` (lines 129-146) — same `rust`, `schema`, `col_type`. Confirmed deliberate via `git log`/`git show 67bee66f` ("64-bit primary keys... `int`/`unsigned` field types map to 64-bit as well"). → **Judgment**: a reasonable compatibility alias, but it doubles 6 of 69 rows in the type mini-language with zero differentiation — a naive user reading mappings.json cannot tell `int` and `big_int` apart or why both exist without the commit message. → **KPI 2**. Severity: **Low**.
5. **FACT**: `src/cli.rs` (1431 LOC, including a ~150-line hand-written `RouteNode` ASCII-tree printer at `:1017-1164` and `format_templates_as_tree` at `:1354-1431`) contains no `#[test]` module and no `mod tests` (`grep -n "#\[test\]\|mod tests" src/cli.rs` → empty); a repo-wide search under `tests/` for `format_templates_as_tree`/`RouteNode`/`parse_key_val` also returns nothing. → **Judgment**: the CLI's only non-trivial pure logic (route-tree collapsing/printing, key:val parsing, template-tree formatting) ships with zero test coverage, in contrast to `loco-gen`'s well-tested generator core. → **KPI 6**. Severity: **Medium**.
6. **FACT**: `src/cli.rs:418-430` (Scaffold kind resolution) and `src/cli.rs:447-459` (Controller kind resolution) are identical `if let Some(kind) = kind { kind } else if htmx {...} else if html {...} else if api {...} else { return Err(...) }` chains, differing only in the error message string. → **Judgment**: a `fn resolve_scaffold_kind(kind, htmx, html, api) -> Result<ScaffoldKind>` helper would collapse both. → **KPI 2, 3**. Severity: **Low**.
7. **FACT**: `loco-gen/src/infer.rs:56-93` (`guess_migration_type`) matches on snake-cased, underscore-split tokens (`"create"`, `"add"`, `"to"`, `"remove"`, `"from"`, `"join"`, `"table"`, `"and"`) and falls through to `MigrationType::Empty` for any unmatched shape (`:91 _ => MigrationType::Empty`) — no error surfaced to the user; this is only visible in the 12 unit tests at `infer.rs:99-231`, several of which encode this silent-fallback behavior as expected (e.g. `test_infer_create_join_table_no_and_separator`, `:194-201`). → **Judgment**: correct as designed and thoroughly tested, but it is inherently a brittle, order/keyword-sensitive DSL — a migration named slightly off-convention silently produces an empty migration rather than failing loudly. → **KPI 4**. Severity: **Low** (mitigated by test coverage, but still a silent-wrong risk for end users of the CLI, who get no test net).

## Library hypotheses

1. **HYPOTHESIS**: `src/cli.rs:1017-1164` (`RouteNode`, hand-rolled ASCII tree printer with `is_leaf`/`is_collapsible`/prefix-formatting logic) → candidate: `ptree` or `termtree`. **Why it might be simpler**: both crates provide generic tree-rendering with box-drawing characters, removing ~100 lines of bespoke prefix/marker string logic (`format_prefix`, `format_next_prefix`, `build_path`). **Risk / why it might not fit**: Loco's tree has bespoke collapsing rules (single-child leaf collapsing onto the parent line, e.g. `/foo/bar GET`) plus inline HTTP-method coloring — a generic tree-printer would need a custom node-formatter callback anyway, so the win may be marginal; also this is a rarely-touched, working piece of code. **NEEDS SPIKE**.
2. **HYPOTHESIS**: Tera's native `{% extends %}`/block system (already used *within* a single kind, e.g. `scaffold/html/base.t` + `view_*.t` use `{% block content %}`) → candidate: extend the same inheritance pattern *across* the html/htmx split so `scaffold/{html,htmx}/view_list.t` etc. become one template with an `is_htmx` conditional block, rather than two files. **Why it might be simpler**: removes the ~900 LOC / near-100%-duplicate template tree documented in Evidence #3, using a feature Tera already supports and the codebase already uses for the `base.t`/page-block relationship. **Risk / why it might not fit**: htmx/html output differs in enough scattered small ways (form method vs `hx-post`, redirect vs HX-Redirect header, PUT+PATCH vs POST) that a single template with many `{% if is_htmx %}` branches could become harder to read than two flat files — this is a real design tradeoff, not a slam dunk. **NEEDS SPIKE**.
3. **HYPOTHESIS**: `loco-gen/src/scaffold.rs:24-75`'s duplicate field-classification loop → candidate: no external crate, but refactor `model::get_columns_and_references` to return a richer struct carrying both `col_type` and `rust_type` per field, consumed by both `model.rs` and `scaffold.rs`. **Why it might be simpler**: eliminates Evidence #2's duplicate `FieldType` match and the reference-column type literals that currently bypass `mappings.json`. **Risk**: `model.rs` is `with-db`-gated while `scaffold.rs`'s rust-type resolution is used for HTML form/view generation that must work independent of some DB specifics — verify no coupling is introduced that breaks feature-gating. **NEEDS SPIKE** (internal refactor, not a crate swap, but flagged since it satisfies the "reinvented wheel" spirit of removing hand-rolled duplication).

## What is genuinely excellent (cited)

- `loco-gen/src/infer.rs:1-14`: an explicit, well-reasoned doc comment on *why* `cruet` and `heck` are both kept and not "consolidated" (differing acronym/digit casing rules, e.g. `HTTPServer` → `Httpserver` under cruet vs `HttpServer` under heck) — this is exactly the kind of decision-rationale comment that prevents future well-intentioned "cleanup" regressions. Rare and valuable.
- `loco-gen/src/mappings.json` + `loco-gen/src/lib.rs:59-201` (`Mappings` impl): a genuinely small, single-source-of-truth field-type mini-language (name → rust type → schema fn → col type → arity) that both `model.rs` and `migration.rs` consume without re-deriving — this is the "economy of concepts" the rubric asks for, done right in the model/migration path (scaffold path is the exception, see Evidence #2).
- Test architecture: 189 total insta snapshot files (`loco-gen/src/snapshots/` for form/view field rendering across all 69 mapping rows, `loco-gen/tests/templates/snapshots/` for full generator output across Api/Html/Htmx × controller/scaffold) combined with `rstest` parametrization (`loco-gen/tests/templates/*.rs`) gives genuinely strong regression coverage over a large combinatorial surface (field type × form context × scaffold kind) with very little test code per case.
- `loco-gen/src/template.rs`: clean, small (216 LOC), single-purpose wrapper around `include_dir` for template collection/local-override lookup, each function documented with `# Errors`, fully covered by its own `#[cfg(test)]` module.

## Top 3 things that would most raise the area's quality

1. Collapse `src/cli.rs`'s two `main` functions into one, parameterized/cfg-branching only at the `Db`/`Jobs` arms rather than duplicating the entire ~150-line match — removes the area's biggest duplication and its single biggest maintenance risk (Evidence #1).
2. Add unit tests for `src/cli.rs`'s pure logic (`RouteNode` collapsing/printing, `format_templates_as_tree`, `parse_key_val`) — currently the only untested corner of an otherwise well-tested area (Evidence #5).
3. Unify the model/scaffold field-classification walk behind one function (Evidence #2) and evaluate Tera template inheritance to shrink the html/htmx template duplication (Evidence #3) — both attack the "three parallel kind-directories" concept-sprawl pattern that runs through the whole generator.
